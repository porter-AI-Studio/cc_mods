第 4 章 · Part 2：安裝與使用

安裝、啟用與管理 Mods

安裝、啟用與日常管理的完整流程

動手前：確認版本與信任

Mods 預設開啟，不需要任何旗標，但要有對的版本。終端機用 claude --version 確認是 v2.1.287 以上；Desktop app 內建自己的 Claude Code，在 Code 分頁的本機 session 輸入 /status，看 Claude Code 那一列，需要 v2.1.286 以上。版本不夠就先更新。

另外有兩個前提會讓 Mod 不載入：在互動 session 裡，如果目錄還沒被你信任，要先回答信任提示，Mod 才會載入；組織的 managed settings 也可能限制能載入哪些 Mod。想知道自己這裡到底能不能載入，官方有專門的疑難排解頁可以查。

取得 Mod 的三種方式

方式一：從 marketplace 安裝

Mod 以 plugin 的形式安裝，所以流程與一般 plugin 完全相同：給 plugin 名稱、@、marketplace 名稱。在 session 裡用 /plugin install，在 shell 裡用 claude plugin install。如果你是在 session 已開著的時候從 shell 安裝或更新，要在那個 session 輸入 /reload-plugins 才會載入；不然就等到下次啟動 Claude Code。

bash
# 在 Claude Code session 裡
/plugin install token-chart@your-org

# 或在 shell 裡
claude plugin install token-chart@your-org

# 在 shell 安裝或更新後，若 session 已開著，要重新載入
/reload-plugins

marketplace 的加入方式、安裝範圍（scope）與保持更新，都沿用 plugin 的官方文件，Mod 沒有額外規則。

方式二：用 --plugin-dir 載入一個目錄

試用或開發時，不必先裝進 marketplace，直接把 plugin 目錄載入一次 session。Anthropic 在 claude-code-playground repo 的 claude-code/mods 目錄放了三個完整的範例 plugin：token-weather（在輸入框上方畫出 context 預報）、blast-radius（扣住 rm -rf、force push 等高風險指令，顯示影響並提供繼續或取消按鈕）與 replay-theater（新增 /replay，逐步重播上一輪的檔案編輯）。官方註明它們照原樣分享，不提供支援。

bash
git clone https://github.com/anthropics/claude-code-playground.git
cd claude-code-playground/claude-code/mods
claude --plugin-dir ./token-weather

這樣載入的 Mod 只存在於這次 session，結束就消失。想長期使用，Complete Guide 示範的做法是把 clone 下來的 claude-code/mods 目錄加成 marketplace，再從 claude-code-playground-mods 安裝。以下是 Complete Guide 示範的寫法，在 mods 目錄裡執行：

bash
claude plugin marketplace add ./
claude plugin install token-weather@claude-code-playground-mods --scope user
ℹ️
本機 marketplace 指向你的 clone

marketplace 指向的是你 clone 下來的目錄，所以把它移動或刪除之後，這個 Mod 就不會再載入。另外，Claude Code 會依版本快取已安裝的 plugin：開發時請一直用 --plugin-dir 指向原始目錄，改完程式碼要先調高版本號再重新安裝，才會更新到已安裝的副本。

方式三：請 Claude 代寫，再搬出來保存

在互動 session 裡描述你要的 Mod，Claude 會依內建的 plugin-authoring skill 寫出來，你也可以輸入 /plugin-authoring 自己載入這個 skill。寫完要經過你的核准才會載入。這類 Mod 有兩個容易踩到的地方：

  • 只存在那一個 session：Claude 代寫的 Mod 只在寫它的 session 載入，而且該 session 的 mods 資料夾超過 cleanupPeriodDays 之後會被 Claude Code 刪掉。想保留，要把目錄複製到自己的位置（例如 ~/mods/git-branch），再用 claude --plugin-dir ~/mods/git-branch 載入，或加入 marketplace 分享。
  • 某些 session 不會載入：沒有人能核准的 session（claude -p、dontAsk 模式）、尚未信任的工作區，以及 Mod 被停用的情況（--safe-mode、--bare、disableAllHooks，或 managed settings 禁止）。

怎麼寫與怎麼改，是第三部分（第 7、8 章）的內容；這裡只需要知道它怎麼被載入。

安裝前先審查：claude plugin validate

Mod 是以你的權限執行的程式碼，所以裝之前要先知道它會做什麼。claude plugin validate 不會執行 Mod，只會讀 manifest 與 hooks module 的原始碼做靜態分析，印出它掛了哪些事件、呼叫了哪些 mods API。先取得 plugin 的檔案（例如 clone 它的 repo），再對該目錄執行：

bash
claude plugin validate ./some-mod

輸出裡的 hooks: 與 calls: 兩行就是重點，官方管理文件給的範例長這樣：

輸出範例
❯ ./register.js hooks: session.start, tool.call, ui.render{component=Pane}
❯ ./register.js calls: $.fs.read, $.http.fetch, $.store.set, $.ui.open

hooks: 是它接收的事件，括號裡是 matcher；calls: 是它要求 Claude Code 做的事。審查時對照下表，看看它的行為是否符合它宣稱的功能：

出現在 calls: 的呼叫代表什麼
$.fs.read、$.fs.write讀寫你的帳號能碰的任何檔案
$.process.run、$.process.spawn以你的身分啟動程式
$.http.fetch發出網路請求
$.env.get、$.settings.read讀環境變數與設定，裡面可能有 API key；輸出會另有 env reads: 列出變數名稱
$.env.set為 Claude Code 與之後啟動的每個指令、MCP 伺服器設定環境變數；會有 env writes: 列出變數
$.model.complete用你的方案或 API key 呼叫模型
$.prompt.submit送出 prompt，也可以當成你自己打的字送出
$.session.send傳訊息給另一個 session、子代理或隊友的 Claude

hooks: 那行也要看：有 tool.call 與 prompt.submit 表示它看得到每一個 tool call 與每一則 prompt，並能改寫；有 tool.check 表示它能在權限提示出現前就核准或拒絕工具呼叫；session.append 表示它能在對話列被儲存前改寫內容。完整的審查思路在第十五章。

⚠️
validate 不是安全稽核

它只告訴你這個 Mod 宣告了什麼事件與呼叫，不保證程式碼無害。拿它來決定要讀哪些程式碼、哪些行為需要解釋，例如一個只顯示 git branch 的 Mod 卻呼叫了 $.http.fetch，就需要理由。同時，Mod 沒有沙箱：就算你開了 Claude Code 的 sandboxing，沙箱隔離的是 Claude 執行的 Bash 指令，Mod 啟動的程序在沙箱之外。

確認它真的載入了

在 Claude Code 輸入 /plugin。如果有非內建的 Mod 已載入，分頁下方會出現一行暗色文字，列出數量與名稱，像 1 mod active · first-mod。裝了卻沒在名單上，就要去查它為什麼沒作用。內建的 Mod 不算在這一行裡，要到 Installed 分頁的 Built-in 底下看；內建 Mod 不能更新或解除安裝，第五章逐一說明。

💬

雷根在 1987 年簽署中程飛彈條約時，引述他所稱的俄國老諺語：trust, but verify（信任，但要查證）。本書借這句話提醒：裝 Mod 前用 claude plugin validate 查看靜態分析列出的 hooks: 與 calls:，裝完用 /plugin 確認它真的載入了。

出處：雷根，〈Remarks on Signing the Intermediate-Range Nuclear Forces Treaty〉，1987 年 12 月 8 日（雷根圖書館逐字稿，原句 “trust, but verify”）。中文為本書自譯；套用到 Mod 安裝是本書改編。

內建的 Mod 並非全部預設開啟。官方表格列出的 cc-plugin-you-should-know（在較長的任務中跑一個旁觀的側邊 agent，發現你可能漏看的事就在輸入框上方顯示提示）預設是停用的，要自己啟用：

Claude Code session
/plugin enable cc-plugin-you-should-know@builtin

停用、解除安裝與緊急關閉

官方依「要停多少、停多久」把關閉方式分成三層，要恢復時只要撤銷同一個設定：

範圍做法連帶影響
單一 Mod在 /plugin 的 Installed 分頁停用或解除安裝該 plugin該 plugin 整個停用
所有已安裝的 Mod、單次 session用 claude --safe-mode 啟動同時停用你其他的客製設定
所有已安裝的 Mod、每次 session在 ~/.claude/settings.json 設 "disableAllHooks": truesettings hooks 與自訂狀態列也一併停止；組織管理的部分照常運作

幾個細節值得記住。第一，disableAllHooks 與組織的 allowManagedModsOnly 停掉的只是 Mod，plugin 本身還裝著，它裡面的 skills、commands、agents 與 MCP 伺服器仍會載入；其他設定與旗標影響的範圍更廣，要看各自的文件。第二，這些設定與 --bare 都停不了內建的 Mod，它們各有自己的關閉方式。第三，如果懷疑某個 Mod 造成問題，用 claude --safe-mode 開一個乾淨的 session 對照最快；但因為內建 Mod 不受影響，「safe mode 就好了」是線索，不是完整診斷。

💡
預覽期的環境變數已經失效

如果你在 early access 期間設過 CLAUDE_CODE_ENABLE_FUNCTION_HOOKS，請移除。v2.1.287 以後的版本忽略它，所以設成 0 並不會讓 Mods 保持關閉。要關就用上表的方式；組織要管就用下一節的 managed settings。

讓 Mod 目錄常駐：CLAUDE_CODE_PLUGIN_DIRS

如果你的 Mod 放在本機目錄，不想每次啟動都打 --plugin-dir，或者你用的 app 沒辦法帶旗標，可以用環境變數 CLAUDE_CODE_PLUGIN_DIRS，效果等同 --plugin-dir。它可以設在環境變數，也可以放進 ~/.claude/settings.json 的 env。路徑要用絕對路徑，多個目錄之間用 : 分隔，Windows 上用 ;。作者自己在 Windows 上就是這樣載入本機 Mod 的，路徑用正斜線（下面的 C:/Users/you/... 是示意路徑，請換成你的實際絕對路徑）：

~/.claude/settings.json
{
  "env": {
    "CLAUDE_CODE_PLUGIN_DIRS": "C:/Users/you/.claude/mods/mod-a;C:/Users/you/.claude/mods/mod-b"
  }
}

這種載入方式不經 marketplace，等於每次啟動都自動帶上 --plugin-dir，適合自己維護的本機 Mod。要和別人共用，仍然走 marketplace。

組織怎麼管：先知道預設值

如果你在組織裡用 Claude Code，管理員可以決定 Mod 是否執行、執行哪些。預設情況（沒有任何 Mod 設定）是：Mods 開啟，使用者可以從 plugin 設定允許的任何 marketplace 安裝含 Mod 的 plugin，也可以用 --plugin-dir 載入目錄。同時，Claude Code 會在使用者安裝的所有 Mod 之前載入內建的守衛 sec-default@builtin（在 /plugin 與 debug log 裡叫 cc-plugin-sec-default），使用者無法關掉它。它在機器有 managed settings，或使用者以 Team 或 Enterprise 方案登入時載入。

這個守衛保護的是組織管理的東西：使用者的 Mod 不能改變組織 managed hooks 收到或決定的內容、系統提示、managed 的 CLAUDE.md 與其他 managed 指示、任何 Mod 讀到的設定，以及 managed MCP 伺服器的工具與說明。除此之外官方的說法是「Everything else is allowed」：使用者的 Mod 仍然能以使用者的權限讀寫檔案、啟動程序、發網路請求、改寫 tool call 與 prompt。

💬

內建守衛只護著組織管理的那一圈，其餘就是官方說的「Everything else is allowed」：使用者的 Mod 仍以使用者的權限讀檔、啟動程序、發網路請求。

想完全不讓使用者自帶的 Mod 執行，就在守衛上設 allowManagedModsOnly，放在 managed settings 的 pluginConfigs 底下：

managed-settings.json
{
  "pluginConfigs": {
    "cc-plugin-sec-default@builtin": {
      "options": {
        "allowManagedModsOnly": true
      }
    }
  }
}

設定後，使用者安裝的 plugin 裡的 Mod、用 --plugin-dir 載入的 Mod 與 Claude 在 session 裡代寫的 Mod，hooks 都不會執行；組織自己的 Mod 與內建 Mod 照常運作，使用者設定檔的 settings hooks、狀態列與 /goal 也不受影響。守衛只讀 managed settings 裡的這個值，所以在使用者、專案或本機設定檔裡寫同一筆沒有效果。更完整的政策取捨，包含 allowManagedHooksOnly、disableAllHooks 與 disableSideloadFlags 的差別，留到第十六章。

小結

安裝一個 Mod 的流程可以整理成幾步：確認版本與信任；從 marketplace 安裝，或用 --plugin-dir 先試一個 session；裝之前用 claude plugin validate 看它掛了哪些事件、呼叫了哪些 API；裝完用 /plugin 確認載入；出問題時從單一 Mod、--safe-mode 到 disableAllHooks 逐層關閉。Claude 代寫的 Mod 要記得搬出來保存，組織則用 managed settings 管控。
