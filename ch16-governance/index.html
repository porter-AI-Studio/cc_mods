第 16 章 · Part 5：安全與治理

團隊導入與治理：審查、管控與取捨

給決策者：先看預設值，再決定要放多寬

上一章的結論是：Mod 的權限等同使用者，個人可以靠自己審查，團隊不行。這一章寫給要決定「團隊要不要開、開多寬」的人。內容以 Anthropic 官方的 Manage mods 與 Manage plugins 兩份管理文件為主，第三方文章只在標明來源時補充；標「作者判斷」的部分是我的看法，不是官方建議。

先看預設值：你現在其實已經開著

依官方文件，Mods 預設就是開的（終端機需 Claude Code 2.1.287 以上，Desktop 是 2.1.286 以上）。使用者可以從任何你的 plugin 設定允許的 marketplace 裝含 Mod 的 plugin，也可以用 --plugin-dir 從目錄載入，Claude 在對話中替他寫的 Mod 也能載入。你現有的 plugin 管控，等於決定了使用者能載入什麼：

你現有的 plugin 管控使用者能載入的 Mod
沒有任何 marketplace、任何目錄的 --plugin-dir、Claude 對話中寫的 Mod
marketplace 白名單白名單內 marketplace 的 Mod，加上任何目錄的 --plugin-dir；對話中寫入 skills 目錄的 Mod，只有白名單含 skills-dir 時才能載入
白名單加 disableSideloadFlags只有白名單內 marketplace 的 Mod

第 15 章已說明：守門 Mod sec-default@builtin 只在機器有 managed settings，或使用者以 Team／Enterprise 方案登入時才載入；用 API key 的人必須靠 managed settings。這決定了後面所有選項是否生效，所以第一步是確認 managed settings 真的送到每台機器。官方管理文件提供的驗證方式是：在受管機器上用 --plugin-dir 載入一個 Mod，看 hook 是否被拒絕、transcript 與 debug log 是否出現守門 Mod 的訊息。

審查清單：每個 Mod 上線前要過的關

官方審查工具是 claude plugin validate，輸出的 hooks: 與 calls: 兩行列出事件與 API 呼叫（範例輸出見上一章）。官方列出要特別看的呼叫如下，我把它改寫成審查表：

在 calls: 看到代表審查時問什麼
$.fs.read、$.fs.write讀寫使用者能碰的任何檔案路徑是否限在專案或自己的資料夾？
$.process.run、$.process.spawn以使用者身分啟動程式指令是否固定？官方範例的政策 Mod 預設就拒絕這兩者
$.http.fetch網路請求目的地是否固定？有沒有「抓下來再執行」？
$.env.get、$.settings.read讀環境變數與設定，可能含 API key輸出的 env reads: 行列出哪些變數？
$.model.complete花使用者的方案或 API key每回合會呼叫幾次？
$.prompt.submit、$.session.send代使用者送 prompt、傳訊息給其他 session是否限制在使用者有感的場合？
hook 為 tool.call、prompt.submit、tool.check看得到並可改寫、核准每個呼叫為什麼需要？
session.append，或掛在 AskUserQuestion 上的 ui.render可改寫儲存前的對話、可重畫詢問對話框為什麼需要？

validate 之外，要補上第 15 章列的三項人工動作，它們來自 Pluto Security 與 ssdnodes 的建議，不是官方要求：讀原始碼（特別是改寫傳給 next 的值的地方）、用 commit 固定你審過的版本、拒絕執行期才抓遠端程式碼的 Mod。marketplace 條目可以用 ref 加 sha（40 字元的 commit）固定第三方 plugin，這是官方 marketplace 格式的功能；developersdigest 與 dev.to 文章也都把它當成團隊核准單一版本的做法。

審查結論要留紀錄。作者判斷：審查是有時效的，marketplace 開啟自動更新後磁碟上的檔案可能改變，審過的版本號與 sha 要連同結論一起存檔。

管控層級：從放任到全關

官方管理文件把可選政策整理成一張對照表，每種都只需要幾個 managed setting：

你要的狀態設定代價
沒有任何使用者安裝的 Mod，settings hook 不動守門 Mod 的 allowManagedModsOnly，且不部署自己的 Mod內建 Mod 不受影響
連你自己的 managed hook 也一起關disableAllHooks: true最寬：managed 的 PreToolUse hook 也不再阻擋，自訂狀態列與 /goal 也停
只有組織自己的 ModallowManagedModsOnly 加上部署自有 Mod需要自己維護 Mod 與分發目錄
核准過的 marketplace 內任何 Modmarketplace 限制加 disableSideloadFlags: true只決定能從哪裡裝，不管載入後的行為
任何 Mod，但由你的政策 Mod 檢查其他 Mod安裝自有 Mod，並與 sec-default@builtin 一起列入 prependPlugins政策 Mod 本身出錯時預設放行，見下文

另有 allowManagedHooksOnly：只有組織的 Mod 與內建 Mod 會載入，而且會擋掉使用者自己 settings 檔裡的 hook，範圍比 allowManagedModsOnly 更廣，設定前官方要求先讀它的「什麼仍會執行」清單。disableSideloadFlags 會在啟動時拒絕 --plugin-dir 與 --plugin-url，並讓 Claude 在對話中寫的 Mod 無法載入，同時也拒絕 --agents 與 --mcp-config。這些設定只有放在 managed settings 才算數，放在使用者、專案、本機設定檔，或 --settings 傳入的檔案都沒有效果。

「只有組織自己的 Mod」是最常見的嚴格模式，官方給的完整 managed-settings.json 如下：

managed-settings.json（官方範例）
{
  "extraKnownMarketplaces": {
    "acme-tools": {
      "source": { "source": "directory", "path": "/opt/acme/claude-plugins" }
    }
  },
  "enabledPlugins": { "acme-guard@acme-tools": true },
  "prependPlugins": ["acme-guard@acme-tools", "sec-default@builtin"],
  "pluginConfigs": {
    "cc-plugin-sec-default@builtin": {
      "options": { "allowManagedModsOnly": true }
    }
  },
  "disableSideloadFlags": true
}

注意一個容易踩的坑：要被視為「組織的 Mod」，plugin 必須同時符合官方三個條件：managed 的 enabledPlugins 設為 true；marketplace 以絕對路徑指向機器上的目錄；marketplace 以相對路徑列出該 plugin，讓 Claude Code 原地載入。從 GitHub、git、URL、npm 複製到快取的 plugin 一律算使用者的，prependPlugins 會略過、allowManagedModsOnly 會拒絕。官方還提醒，這個目錄與其上層目錄只能由管理員寫入，任何能寫入的人都能改寫你的 Mod；而 admin console 送出的 managed settings 能帶這些鍵，卻無法把目錄放到機器上，仍需要 MDM 之類的方式分發。

marketplace 管控：先決定能從哪裡裝

Mod 是 plugin，所以 plugin 的管控也同樣適用。官方列出的重點：strictKnownMarketplaces 是來源白名單（別名 allowedMarketplaces），blockedMarketplaces 是黑名單且優先檢查；兩者檢查的是 marketplace 的來源，不是 marketplace 裡的單一 plugin 條目。黑名單的寫法例如：

blockedMarketplaces（官方範例）
{
  "blockedMarketplaces": [
    { "source": "github", "repo": "untrusted-org/*" }
  ]
}

幾個決策者要知道的細節，都來自官方管理文件：空陣列 [] 會鎖掉所有來源，包含官方 marketplace；設了白名單而沒有 {`{ "source": "skills-dir" }`} 項目時，使用者放在 skills 目錄的 plugin 會停止載入；白名單與黑名單在下載前、以及每次 session 啟動時都會檢查，來源不再符合的已安裝 plugin 不會載入；enabledPlugins 設為 false 可在所有範圍封鎖並隱藏某個 plugin。strictKnownMarketplaces 本身擋不了 --plugin-dir，所以要搭配 disableSideloadFlags。

managed settings 有三種送達方式：admin console 的 server-managed、MDM、本機的 managed-settings.json 檔。官方說預設同一台機器只會套用其中一種，順序是 server-managed、MDM、檔案，取第一個有送出政策鍵的來源；只要 server-managed 送了任何一個不相關的鍵，MDM 與檔案裡的 plugin 鍵就會被忽略，除非把 managedSourcesBehavior 設為 "merge"。先用檔案試辦、後來開 admin console 的團隊最容易踩到。

自己的政策 Mod：能做什麼、會怎麼壞

當你需要「允許某些人的 Mod、拒絕另一些」或「記錄 Mod 做了什麼」，就要寫自己的政策 Mod。它在每個 Mod 載入前會收到 plugin.register 事件，裡面的 e.uses 就是 validate 印出的清單，可以據此用 {`{ refuse }`} 擋掉；它也能用 API 呼叫的名字（如 fs.write）攔截所有 Mod 的對應呼叫。重點在失敗行為：官方文件指出，如果這個檢查 hook 拋例外或超時，Claude Code 會略過它，檢查就變成放行。要改成失敗時拒絕，就要加 .catch：

acme-guard/hooks/register.js（官方範例，失敗即拒絕）
const BLOCKED_CALLS = ['process.run', 'process.spawn']
// The same check as before, moved into a function of its own
async function checkMod($, e, next) {
  const blocked = e.uses.calls.filter((call) => BLOCKED_CALLS.includes(call))
  if (e.tier === 'user' && blocked.length > 0) {
    return { refuse: 'Acme policy: mods may not call ' + blocked.join(', ') }
  }
  return next(e)
}
export function register(on) {
  // The handler runs only when checkMod throws or exceeds its time limit
  on('plugin.register', checkMod).catch(async ($, e, next) => {
    // Let your organization's mods and built-in mods load
    if (e.tier !== 'user') return next(e)
    // Refuse the user's mod that couldn't be checked
    return { refuse: 'Acme policy check failed, so this mod was not loaded' }
  })
}

官方也說明政策 Mod 並非不會被繞開：背景 worker 若當掉三次，Claude Code 會卸載所有非內建 Mod，包含你的，直到使用者重新載入或開新 session；--safe-mode 也會停掉所有已安裝的 Mod，連你的也不例外。相對地，守門 Mod 本身是「失敗即拒絕」：讀不到 managed settings 就拒絕所有使用者的 Mod。作者判斷：政策 Mod 是補強工具，不是唯一的防線；真正不能失手的限制，仍要用 managed settings 的鍵來做。

💬

政策 Mod 的檢查若拋例外或超時就會變成放行；加上 .catch，才是「檢查不了的 Mod，就當作沒通過」。

取捨：三種常見立場

立場適合得到失去
全關（allowManagedModsOnly，不部署自有 Mod）受法規約束、無人力審查的團隊最小攻擊面，settings hook 與 skills 照常運作使用者做不了任何面板、狀態列、客製指令
只放組織自己的 Mod有平台團隊、想提供標準化工具可控、可稽核、能攔截其他 Mod維護成本，以及分發目錄的管理
白名單 marketplace 加審查想保留社群生態、又要有來源控制彈性最大審查負擔，且載入後的行為仍靠審查，不靠機制

這張表是作者判斷。有兩點要提醒：第一，所有管控都不是沙箱，官方管理文件明說「沒有任何一項控制把 Mod 關進沙箱」；第二，網路政策只涵蓋 Mod 的 $.http.fetch（條件是組織政策不允許 WebFetch），不涵蓋 $.process.run 啟動的程式；CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC 從 v2.1.288 起也不再停止使用者安裝的 Mod 的 $.http.fetch。

💬

載入管控決定誰能進門；進門後要限制 Mod 的 API 呼叫，還得檢查政策與子程序這兩條邊界。

來源之間的差異與限制

  • 撤銷是否立即：agentpatterns.ai 的文章主張政策收緊後既有安裝「要等下次 refresh」才失效；官方管理文件則寫白名單與黑名單在 session 啟動時對已安裝 plugin 再檢查一次。兩者衝突時我採官方，但仍建議自己實測「撤銷一個來源後，下次 session 是否真的不載入」。
  • 設定鍵名稱：同一篇文章用 strictPluginOnlyCustomization 搭配 mcpServers 的寫法；官方的陣列值是 skills、agents、hooks、mcp，以官方為準。
  • 早期文章的過時資訊：2026 年 9 月的文章（例如 wavect.io 的德文文章）描述的是需要 CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 的早期測試期；官方現在說 2.1.287 以後會忽略這個變數，設成 0 也關不掉，要改用 allowManagedModsOnly。
  • API 還在變：官方文件寫著文件與 GitHub 上的型別宣告可能比你安裝的版本舊；有些功能有最低版本需求，例如 isDeferred: false 需要 v2.1.293。導入前先固定 Claude Code 版本，升級後重跑測試。

建議的導入順序（作者判斷）

  1. 先確認守門 Mod 會載入：每台機器都收到 managed settings，用 claude --debug 與 --plugin-dir 驗證政策有生效。
  2. 先關再開：先設 allowManagedModsOnly 與 disableSideloadFlags，再逐一核准 Mod。wavect.io 建議在可控的試辦專案、用合成資料、指定負責人與回復流程，不要假設有穩定的支援合約。
  3. 從低風險開始：像第 13 章的用量儀表、第 14 章的 next-steps 這種不連網、不啟動程式的 Mod，審查最簡單。先用三個左右的 Mod 試辦，逼自己把版本固定、命名與審查流程想清楚。
  4. 留稽核與回復：用政策 Mod 或 debug log 記錄 Mod 載入與寫檔；確認 --safe-mode 能作為「Mod 造成問題」時的第一個排查步驟。
  5. 用成本衡量，不是用展示：wavect.io 提出用「每個通過驗收的任務的總成本」比較有無 Mod，包含模型成本、開發與審查時間；這是它的評估方法，不是官方公式。

驗證政策是否生效時，官方建議在測試機上這樣做：

驗證政策（官方建議的檢查方式）
claude --debug
claude --plugin-dir ./any-mod

用 claude --debug 讀 debug log：你的 Mod 會出現 tier prepend；使用者的 Mod 會被 refused by cc-plugin-sec-default 拒絕；--plugin-dir 則會以 --plugin-dir is disabled by your organization's managed settings (disableSideloadFlags) 開頭的訊息結束。

⚠️
治理不等於防護

以上所有設定管的是「誰能載入」，不是「載入後做什麼」。即使只放行組織自己的 Mod，那份 Mod 仍有使用者的全部權限。所以審查、版本固定與稽核，不能因為有了 managed settings 就省略。

小結

全書到這裡完成了一條線：從 Mod 是什麼、怎麼裝、怎麼寫，到它沒有沙箱、團隊該怎麼管。對決策者而言，記住兩件事就夠：預設是開的，而管控是你主動加上去的；管控決定誰能載入，審查才決定載入的東西可不可信。書中出現的主要名詞整理在 名詞解釋。
