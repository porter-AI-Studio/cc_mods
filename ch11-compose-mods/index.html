組合多個 Mod：hook 順序與 noun contract

拆解 hook 順序與 noun contract 的介面契約

⚠️
本章素材有限

公開資料對「多個 mod 如何組合」的說明偏少：官方文件講了順序與失敗處理，noun contract 則主要出自 Claude Code 儲存庫裡內建 mod 的 README，而且那份 README 自己標示為 early access。其中一些早期描述，例如「只有啟用 function hooks 才會載入」，已經被 v2.1.287 預設開啟取代。以下內容一律以官方文件與你所用版本產生的型別宣告為準。

只裝一個 mod 時，hook 的順序不成問題。同時裝三個，而且其中兩個都掛 tool.call，誰先看到事件、誰能擋下誰，就會直接改變結果。

順序：先註冊的包在外面

同一個事件上的 hook 組成一條中介鏈。最外層的 mod 先看到事件、最後看到結果，並決定後面的 mod 要不要跑；後面的 mod 沒辦法阻止前面的 mod 看到事件。Preview 階段的設計文章用一個式子描述這種洋蔥結構：

on 的註冊順序就是巢狀順序
on(X, A)
on(X, B)
on(X, C)
→ X = A(B(C(bottom)))

Claude Code 依來源決定誰排在外面：

💬

外層先看到事件、最後看到結果：後面的 mod 擋不了前面的，前面的卻能決定後面的跑不跑。

  1. 內建守門器 sec-default@builtin、組織列在 prependPlugins 的 mod，以及其他屬於組織、又不在 appendPlugins 的 mod
  2. 你自己安裝的 mod
  3. 組織列在 appendPlugins 的 mod
  4. 其他內建 mod

你安裝的 mod 之間，宣告在 dependencies 的 mod 排在依賴它的 mod 後面；同一個模組內，依 register 呼叫 on 的順序。順序看的是設定中的位置，不是安裝的先後。設定檔裡的 PreToolUse 也有固定位置：managed settings 的在第一個 mod 的 tool.call 之前，擋下就是定案；其他設定檔與 plugin 的 hooks/hooks.json 則在最後一個 mod 呼叫 next 之後才跑。

另外，每個 mods API 方法本身也是一個事件。外層的 mod 可以觀察、改寫或拒絕你的 $.fs.read，這是組織限制 mod 能力的做法。內層不能反過來。

鏈是串行的，每一環都要等下一環的 next(e) 完成。社群在 2.1.260 preview 上的實測（單一機器的回報，不是基準測試）顯示：25 個直通 hook 只比沒有 hook 多約 5 毫秒，但 8 個各做 300 毫秒工作的 function hook 串在一起是 2427 毫秒，而 8 個平行的 command hook 只要 640 毫秒。意思是：把 hook 寫成輕量檢查，慢的工作不要塞在鏈裡。

💬

社群單機實測：25 個直通 hook 只多約 5 毫秒，8 個各做 300 毫秒工作的 function hook 串起來卻要 2427 毫秒；鏈上每一環都要等下一環，慢的工作別塞進鏈裡。

失敗：決定要放行還是拒絕

hook 丟例外、逾時或回傳形狀錯誤，預設會被跳過：還沒呼叫 next 就失敗，就由下一個 handler 取代；呼叫 next 之後才失敗，結果照舊。守門的 hook 跳過等於放行，所以要用 .catch 改成失敗就拒絕：

讓守門 hook 失敗時拒絕
// on returns a registration, and .catch attaches a handler to that one hook
on('tool.call', { tool: 'Bash' }, guard).catch(async ($, e, next) => {
  // guard had already called next, so return what came back
  if (next.called) return next(e)
  // next.error.kind says why the handler was asked, such as 'throw' or 'timeout'
  return { deny: 'The command guard failed, so this command was not run: ' + next.error.kind }
})

next.called 讓 handler 分辨守門器是在呼叫 next 之前還是之後失敗。.catch 的時限只有 1 秒，handler 自己再失敗，hook 會被當成沒有 handler。反過來，只負責觀察的 mod，例如計量條，應該失敗時放行：.catch(($, e, next) => next(e))，免得一個畫面上的 bug 擋住你的工作。tool.check 與 plugin.register 則不同，在 next 之後回傳的拒絕仍然有效，不必檢查 next.called。

💬

hook 失敗時 Claude Code 預設是跳過它：守門 hook 要在失敗時仍然拒絕，就得自己用 .catch 把預設改回來。

另一種失敗是迴圈。hook 觸發的事件如果來自它自己呼叫的 mods API，這個 hook 會被跳過，next.error.kind 是 re-entry，這需要 Claude Code v2.1.292 以上。

noun contract：mod 之間的介面

mods API 的 $.fs、$.ui 這些命名空間，內部稱為 noun。mod 可以掛 engine.create（mods API 被建出來給這個 mod 時觸發），回傳一個多了新 noun 的 API，讓別的 mod 能呼叫它提供的方法。例如內建的 telemetry 在引擎沒有 $.telemetry 時，把它加進去，寫法是把底下已有的值放在後面展開：{ ...{ telemetry }, ...beneath }，所以底下既有的 telemetry 不會被蓋掉。

新增一個 noun 的 mod 同時擁有它的型別，並且只放一個地方：types/index.d.ts。這份宣告檔不 import 任何東西，匯出組成 noun 的型別，並在 claude-code 的 EngineInterface 上宣告那個 noun。這就是合約，約束有三條：

💬

noun 的合約只放在 types/index.d.ts 一個地方：提供者與呼叫端讀同一份檔案，型別就不會各說各話。

  • 合約是這個 noun 唯一的宣告。提供者自己的 hook 從該資料夾 import 型別，engine.create 回傳的值會對照 EngineInterface['telemetry'] 檢查，實作不會偏離呼叫端讀到的型別。
  • 呼叫別人的 noun，讀同一份檔案，不要複製。內建的 diff 呼叫 $.telemetry.log，型別就來自 telemetry 的合約。
  • 測試要用到別人的 noun 時，先放一個 provider，也就是一個用 engine.create 加上該 noun 的 inline plugin，再替呼叫做 stand-in。沒有 provider，$ 的建構會拒絕那個 hook，並指出沒人提供的 noun 名稱。
測試裡替另一個 mod 的 noun 做 stand-in
on('telemetry.log', ($, e) => ({ value: undefined }))

依賴別人 noun 的 plugin，在 plugin.json 用 dependencies 宣告：

plugin.json 的 dependencies 欄位
"dependencies": ["secrets-vault"],

宣告後，Claude Code 載入時會在 .claude-plugin/types/ 為每個依賴放一個以 plugin 命名的資料夾，裡面的 index.d.ts 就是那個 plugin 對 mods API 的補充。提供者不在時要有退路：diff 在沒有 $.telemetry 時，只是丟掉那些資料列，其他行為不變。

組織管理員用同一套機制建立保護。他們把守門 mod 排進 prependPlugins，守門 mod 也可以掛 engine.create 決定哪些 noun 存在。sec-default 則是在最外層用 next.to(e, "append") 跳過使用者那一層，只有 managed 層的 mod 才能呼叫這個方法。設定時要注意：

設定位置
"prependPlugins": ["acme-guard@acme-tools", "sec-default@builtin"]

一旦 managed settings 定義了 prependPlugins，那份清單就是整個 prepend 層，要讓內建守門器載入，就得把它寫進去。第 16 章會回到團隊治理。

小結與下一章預告

組合 mod 要記三件事：外層先看到事件，守門 hook 要有 .catch，共用的功能放進一份 noun contract 讓呼叫端與提供者讀同一個檔案。第 12 章回到單一 mod，用三個完整案例（守門器、輪次計量條與 /pyenv）把前面各章用到的東西串起來。
