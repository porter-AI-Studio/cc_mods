測試、驗證、除錯與分享

測試、除錯與安全分享你自己的 Mod

上一章你學會了事件與 $ 的組合。這一章處理寫完之後的事：怎麼在不啟動 session 的情況下確認 mod 做了什麼（驗證）、怎麼自動化測試（測試）、它沒反應時怎麼找原因（除錯），以及怎麼交給別人（分享）。四件事用到的都是 Claude Code 內建的工具，不需要另外安裝 Node.js 或打包器。

驗證：claude plugin validate

驗證不執行你的程式，也不開 session。它讀 manifest，並對 hooks module 的原始碼做靜態分析，也就是 Claude Code 載入 mod 時做的同一套分析。

bash
claude plugin validate ./first-mod

輸出有三種資訊要看。hooks: 那行列出你掛了哪些事件，括號裡是 matcher；calls: 那行列出你呼叫的每個 mods API 方法；沒掛 .catch 的守門 hook 會多一行，例如 gating hook without .catch: tool.call。讀環境變數或用 $.state 時還會出現 env reads: 與 state reads: 之類的行。

first-mod 的驗證輸出
❯ ./register.js hooks: session.start, tool.call, command.run{command=tally}, ui.render{component=Spinner}
  ❯ ./register.js calls: $.command.register, $.ui.invalidate

✔ Validation passed

事件名稱拼錯時，驗證會報錯，例如 "tool.calls" is not an event。如果你想掛的事件沒出現在 hooks: 那行，Claude Code 載入時也不會呼叫它。這個指令另有兩個旗標：--strict 把警告當錯誤，--json 輸出機器可讀的報告，兩者都適合放進 CI。

💬

事件名拼成 tool.calls，claude plugin validate 會直接告訴你它不是事件；不驗證的話，這個 hook 只會永遠安靜地不觸發。

要讓靜態分析找得到每個 hook 與每個呼叫，程式必須遵守這幾條：

  • mods API 呼叫寫成完整的 $.store.get('notes')。把 $.ui 指派給變數會失敗：$.ui is used as a value，解構也不行。
  • 可以把 $ 傳給同一個檔案頂層宣告的函式，傳給方法、hook 內部定義的函式或從別的檔案 import 的函式則會失敗。
  • on 的事件名稱必須是字串常值，用變數或迴圈會報 the event name passed to on() is not a string literal。
  • register 裡不要再宣告第二個叫 on 的變數或參數。
  • 只能用相對路徑 import plugin 資料夾內的檔案，唯一允許的裸 import 是 claude-code。
  • 檔案一律是 ES module：用 import 宣告，不用 require，也不用動態 import()。

測試：claude plugin test

在 mod 資料夾執行 claude plugin test，它會跑底下所有檔名以 .test.ts 或 .test.tsx 結尾的檔案，不需要登入、網路或 session，有測試失敗時以狀態碼 1 結束。測試會「觸發」你的 hook 處理的事件，再檢查結果。下面這個測試觸發兩次工具呼叫，再執行 /tally：

first-mod/tests/first-mod.test.ts
import { expect, test } from 'claude-code/testing'

test('/tally reports the tool calls the mod has seen', async ($, on) => {
  // Answer each tool call in Claude Code's place, so no tool runs
  on('tool.call', () => ({ result: 'ok' }))

  // Fire two tool calls, which the mod's tool.call hook counts
  await $.tool.call({ tool: 'Bash', command: 'ls' })
  await $.tool.call({ tool: 'Read', file_path: 'README.md' })

  // Run /tally and check the text its hook returns
  const answer = await $.command.run({ command: 'tally', args: '' })
  expect(answer.text).toBe('Claude has made 2 tool calls since this mod loaded')
})
claude plugin test 的輸出
tests/first-mod.test.ts:
(pass) /tally reports the tool calls the mod has seen [22.87ms]

 1 pass
 0 fail
Ran 1 test across 1 file. [0.19s]

測試套件底下沒有真正的 Claude Code，所以 mod 呼叫 next 之後需要有人接手回答。測試裡用 on 註冊的 hook 排在你的 mod 之後，扮演 Claude Code：上面那行 on('tool.call', () => ({ result: 'ok' })) 就是「代替 Claude Code 回答工具呼叫，所以沒有任何工具真的執行」。沒人回答的呼叫會直接丟錯，訊息是 nothing beneath the plugins answers。

有幾個容易踩的規則。第一，stand-in hook 要在測試的第一個 $ 呼叫之前註冊，否則會看到 on("tool.call") after the test first called $。第二，替 $ 方法（例如 $.process.run、$.command.register）做的 stand-in 要回 { value: ... }，直接回裸結果會被拒絕。第三，每個測試預設 5 秒，需要更久就在測試裡設 timeoutMs。第四，內建 mod 的原始碼附有測試，例如 diff 用 mock.clock(on)、mock.store、mock.env 模擬時間、儲存與環境變數，是最好的範本。

💬

測試裡的 stand-in 是排在 mod 之後的替身：mod 呼叫 next，有人接，就沒有任何工具真的執行；沒人接，就丟錯。

畫面類的 mod 用 $.ui.mount 把 render site 掛起來，再用 find 找元素。下面的 edit-count 測試取自第三方教學：

tests/edit-count.test.ts
import { expect, test } from 'claude-code/testing'

test('the band counts Edit and Write calls', async ($, on) => {
  // Answer each tool call in Claude Code's place, so no tool runs
  on('tool.call', () => ({ result: 'ok' }))

  await $.tool.call({ tool: 'Edit', file_path: 'a.ts' } as any)
  await $.tool.call({ tool: 'Read', file_path: 'a.ts' } as any)

  const ui = await $.ui.mount({
    plugin: 'edit-count',
    surface: 'terminal',
    component: 'AbovePrompt',
    props: { hasSurvey: false, isWorking: false, maxRows: 10, bodyColumns: 120 },
  } as any)
  expect(await ui.find({ type: 'Text', text: /edited this session: 1/ })).toBeDefined()
  await ui.unmount()
})

除錯：mod 沒反應的時候

開發迴圈很短：用 --plugin-dir 載入資料夾後，存檔就會熱重載 hooks module，並重新執行一次 register。

bash
claude --plugin-dir ./first-mod     # 載入資料夾，存檔就熱重載
claude --debug                      # 啟動時加上，log 會寫出被跳過的 hook 與被拒絕的畫面
claude plugin validate ./first-mod
claude plugin test

重載有一個副作用：模組變數會歸零，所以畫面依賴的值要放進 $.state（它在整個 session 都留著），不要放在模組變數。長時間執行的非互動 session，可以設環境變數 CLAUDE_CODE_PLUGIN_DIR_WATCH=1，讓它在存檔時重載 --plugin-dir 的 mod。

💬

熱重載會讓模組變數歸零，$.state 整個 session 都留著：畫面依賴的值，要放進後者。

mod 沒作用時，照下表由上往下查：

症狀可能原因做法
/plugin 沒有列出 mod資料夾未被信任、用了 --safe-mode 或 --bare、設了 disableAllHooks信任資料夾，不帶旗標重啟；載入成功時 /plugin 會有 1 mod active · first-mod 這類一行
hook 被跳過，沒有明顯錯誤它丟了例外，例如把 $.plugin.name 這個屬性當函式呼叫執行 claude --debug，找 my-mod: tool.call hook skipped: threw Error: boom 這類一行
畫面沒出現回傳的元素樹沒通過驗證debug log 找 a hook returned a tree that does not validate
面板不開空間不夠，自動開的面板要 144 欄加寬視窗，或在 isPlaced 為 false 時畫在色帶上
終端機正常、Desktop 不行Desktop 自帶一份版本，部分元素只有終端機有用 /status 查版本，依 e.surface 分支
VS Code 或 claude -p 看不到畫面這兩處不畫 mod 介面改成逐字稿裡的一行，或指令回傳的 text

hook 丟例外、逾時或回傳形狀錯誤時，Claude Code 的預設是跳過它：還沒呼叫 next 就失敗，下一個 handler 會取代它；已經呼叫 next 之後才失敗，結果照舊。對守門 hook 來說「跳過」等於放行，所以守門 hook 要加 .catch 改成失敗就拒絕，下一章與第 12 章會示範。

💡
我自己踩過的三個坑

這是我的 mod 開發筆記，不是官方文件：$.prompt.submit 不能送 / 開頭的文字，要執行 slash 指令得改用 $.command.run({ command, args })；測試裡替 ui.toast 做 stand-in 要回傳 { value: undefined }，不能回 {}；測試用的 tier() 只接受 prepend、user、append、builtin。

分享：mod 就是 plugin

mod 的發行方式與一般 plugin 相同，依對象選擇：

對象做法
幾個人直接給 plugin 資料夾或 .zip
你的團隊放進自己的 marketplace，例如一個私有 repo；可把它登記在 repo 的設定裡，讓在那個 repo 工作的人都用得到
整個組織由管理員透過 managed settings 安裝
所有人公開 marketplace 的 repo，或投稿到 Anthropic 的目錄

marketplace 只需要在 .claude-plugin/ 裡放一個 marketplace.json，推到 GitHub 就成立：

.claude-plugin/marketplace.json
{
  "name": "my-mods",
  "owner": { "name": "you" },
  "plugins": [{ "name": "safe-shell", "source": "./" }]
}
使用者端
/plugin marketplace add your-org/my-mods
/plugin install safe-shell@my-mods
/reload-plugins

上面第二行裡的 safe-shell 換成你的 marketplace.json 裡列的 plugin 名稱。如果使用者在 session 開著時從 shell 安裝，要在該 session 執行 /reload-plugins 才會載入，否則等下次啟動。發行前有三件事要確認：

  • plugin.json 的 name 不能長得像 Anthropic 自己的，例如以 claude- 開頭，claude plugin validate 會擋下來。
  • Claude Code 依版本快取已安裝的 plugin，所以改了程式要先遞增 version 再重新安裝，使用者那邊才會更新。開發時請一直用 --plugin-dir，不要用已安裝的副本。
  • 事件與方法會隨版本改變，在 README 寫清楚你測試過的 Claude Code 版本。
⚠️
驗證通過不等於安全

通過只代表引擎讀得懂這份程式碼。對別人的 mod，先執行 claude plugin validate 看 hooks: 與 calls:，凡是出現 $.process、$.http、$.fs.write、$.env 與 $.model 的地方，再去讀原始碼。mod 沒有沙箱，權限跟你一樣，第 15 章會專門討論。

小結與下一章預告

驗證看「它碰了什麼」，測試看「它做了什麼」，debug log 看「為什麼沒做」，marketplace 解決「怎麼給別人」。下一章處理多個 mod 同時存在的情況：hook 的執行順序怎麼決定，以及一個 mod 如何把自己新增的 namespace 當成合約交給其他 mod 使用。
