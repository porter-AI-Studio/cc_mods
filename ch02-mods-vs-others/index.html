第 2 章 · Part 1：認識 Mods

Mods 與 hooks、skills、plugins、MCP 的分工

哪些事該用 Mod，哪些事用更輕的工具就夠

先釐清：plugin 是盒子，不是並列的功能

這五個名詞常被擺在同一排比較，但其中 plugin 的層次不一樣。官方的說法是：Mod 本身就是一種 plugin，一個 plugin 可以同時放 skills、settings hooks、Mod、commands、agents 與 MCP 伺服器，所以 Mod 可以和 skill、MCP 伺服器放在同一個 plugin 裡發行。換句話說，plugin 是「打包與發行的單位」，其他四個才是「Claude Code 被擴充的方式」。

這也是為什麼第一章說 Mod 以 plugin 的形式安裝：hooks/hooks.json 裡用 modules 指向你的程式碼，同一個檔案也可以照舊放 settings hooks。官方 Hooks reference 還特別註明，settings hooks 會和 Mod 並存運作；管理員文件則直接寫「Nothing about them is deprecated」，也就是沒有任何一項被棄用。Mod 不是來取代它們的。

表中的 skill 與 MCP 各有專章可查官方文件，這裡只需要記住一條判斷線：skill 與 MCP 都是「給 Claude 東西」，settings hook 與 Mod 才是「攔在事件的路上」。skill 給的是文字，MCP 給的是工具，兩者都不碰 Claude Code 自己的行為；只有 hook 這一側能改變事件的走向。而在 hook 這一側，Mod 比 settings hook 多出的就是「在 Claude Code 程序內執行」帶來的能力。

Mod 與 settings hook：同一件事怎麼寫

兩者最容易被混淆，因為「擋掉危險指令」兩邊都做得到。先看 settings hook 的寫法。官方 Hooks reference 的範例，在設定裡用 matcher 與 if 縮小範圍，只在 Bash 的 rm * 指令出現時才啟動腳本：

settings.json（settings hook）
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(rm *)",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh",
            "args": []
          }
        ]
      }
    ]
  }
}
.claude/hooks/block-rm.sh
#!/bin/bash
# .claude/hooks/block-rm.sh
COMMAND=$(jq -r '.tool_input.command')

if echo "$COMMAND" | grep -q 'rm -rf'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "Destructive command blocked by hook"
    }
  }'
else
  exit 0  # no decision; normal permission flow applies
fi

這是一個在 Claude Code 外面啟動的 shell 程序：從 stdin 讀事件的 JSON，用 jq 解析，再用輸出的 JSON 回覆決定。官方註明這類範例需要先安裝 jq。

Mod 的寫法則是一個函式，直接拿到事件物件。這是官方 React to events 的範例，拒絕 force push 並告訴 Claude 原因（注意它擋的是 git push --force，和上面擋 rm -rf 是不同的規則，比的是寫法，不是功能對等）：

hooks/register.js 內的 hook
// The matcher limits the hook to Bash calls, so e.command is the shell command
on('tool.call', { tool: 'Bash' }, async ($, e, next) => {
  if (/git push .*--force/.test(e.command)) {
    // Returning without calling next answers the event, so the command never runs
    return { deny: 'Force pushes are not allowed in this repository. Push to a new branch instead.' }
  }
  // Every other command goes on to the permission check and then to Bash
  return next(e)
})

兩者擋下的結果其實相似，所以「Mod 才能擋指令」是錯的。Complete Guide 引用 wavect 的 Kevin Riedl 的一句話很貼切：「Mods do not invent the ability to stop an action.」settings hook 一直都能阻擋。Mod 新增的不是「擋」，而是下面這幾件事。

💬

Mod 沒有發明「擋下」這項能力；settings hook 一直都擋得住，Mod 新增的是畫面、記憶，以及事件的前後同處。

Mod 多出來的能力

  • 在介面上畫東西：settings hook 只能顯示文字訊息；窗格、橫帶、按鈕與輸入框只有 Mod 畫得出來。
  • 狀態留在記憶體裡：Mod 的 hook 共用檔案裡的變數，也可以把狀態存進 $.store；command 型的 settings hook 每次都是新程序，想保留東西得自己寫檔。
  • 事件的前後在同一處理：Mod 的 hook 可以 await next(e)，在同一個函式裡看到工具跑完的結果再回應；settings hook 要分成 PreToolUse 與 PostToolUse 兩個事件、兩支腳本。
  • 新增立刻執行的指令：/command 直接執行你的函式，不需要 Claude 的回合。
  • 改寫 prompt 文字、重繪介面、介入模型請求：prompt.submit、ui.render、turn.step 這類事件由 Mod 處理，Complete Guide 也指出 settings hook 改寫不了你的 prompt 文字。
⚠️
它也有代價：Mod 是程式碼，不是設定

settings hook 的行為完全寫在設定檔與腳本裡，要審查只要讀設定與腳本。Mod 是在 Claude Code 程序裡執行的函式，會看到每一則 prompt 與 tool call；它的 hook 在呼叫 next 之前失敗時預設被略過，守門類的 hook 因此不再阻擋（等於放行），要自己加 .catch 才會改成失敗時拒絕（第三章會講失敗處理）。拿 Mod 做安全守門前，要先想清楚這一點。

Skill 與 MCP：給 Claude 東西，不改 Claude Code

如果你的需求是「Claude 做某件事時要照我的流程」，那是 skill 的工作：它是一份 Markdown 指示，Claude 依需要讀進來。如果需求是「Claude 要能查工單、連資料庫、呼叫外部系統」，那是 MCP 伺服器的工作：它在 Claude Code 外面當一個程序，把工具交給 Claude。兩者都沒有改變 Claude Code 的事件流程或介面。

幾份素材的選擇原則一致，整理成對照：

  • 團隊的 code review 流程，或一直在重複解釋的指示：skill。
  • 查工單、查資料庫、接外部系統：MCP。
  • 已有一支現成腳本，要在工具執行前後檢查、阻擋或記錄：settings hook。
  • 要在對話旁邊放互動面板、在輸入框上方放即時顯示、自訂指令或改寫事件：Mod。
  • 要把以上這些打包發行給別人：plugin。

先用最輕的工具

能力重疊的時候，該選哪一個？Complete Guide 的作者提出一個「階梯」做法：由輕到重依序是一段指示（CLAUDE.md 之類）、一個設定或狀態列、一個 hook、最後才是 Mod，只有下面那一階做不到時才往上爬。德文的團隊導入文章也有相同的主張，並且更保守：以能滿足驗收條件、介入範圍最小的機制為先，例如外部服務先用 MCP 接上，再判斷 Mod 是否真的補了缺口。

這是兩篇第三方文章的建議，不是官方規定；但理由很實際。同一篇文章說到，他們自己的經驗是曾經兩次從最上面一階開始做，後來發現其中一個東西用一行指示就能處理，另一個放進狀態列更適合。Mod 的成本不只是寫程式，還包括它是會看到你所有 prompt、以你的權限執行的程式碼，以及 API 可能隨版本調整的相容成本。

ℹ️
和 hooks 一起用時，誰先執行？

同一個 tool call 上同時有 Mod 與 settings hook 時，順序是固定的：managed settings 裡的 PreToolUse hook 比任何 Mod 的 tool.call 先執行，它擋下的呼叫是最終結果；其他設定檔與 plugin 的 PreToolUse hook 則在最後一個 Mod 呼叫 next 之後才執行。如果 Mod 沒呼叫 next 就直接回答，這些 hook 就不會執行。完整的執行順序在第十一章再展開。

一次看懂：我該寫 Mod 嗎

實際決定時，可以用這三個問題當篩子：

  1. 我要的東西需要畫在畫面上，或需要自己的指令與對話框嗎？是，就是 Mod。
  2. 我需要在同一處同時看到事件與結果，或在事件之間記得狀態嗎？是，Mod 很可能比 settings hook 合適。
  3. 以上皆非，只是阻擋、放行或記錄，而且我已有現成腳本？用 settings hook；只是想讓 Claude 照流程做事？用 skill；要接外部系統？用 MCP。

第 3 點的答案是「Mod 不一定是最佳解」，這在實務上才是常態。這本書教你寫與管理 Mod，但不鼓勵為每件小事都寫一個。

💬

值得寫的 Mod，是你先試過更輕的工具、發現它們真的做不到之後，才動手的那一個。

小結

Plugin 是發行的盒子；skill 與 MCP 給 Claude 說明書與工具；settings hook 與 Mod 則攔在事件的路上，差別在於 Mod 在 Claude Code 程序內，因此能畫介面、保留狀態、新增指令並在同一處看到事件的前後。選擇時先用最輕的，只有在需求落在執行路徑或介面互動時，才值得付出寫 Mod 的成本。
