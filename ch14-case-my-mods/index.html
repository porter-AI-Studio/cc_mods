我的四個 Mod：obs-log-timer、herdr-watch、file-collision、next-steps

作者每天在用的四個 Mod：三個自製、一個社群

前兩章的案例來自官方文件與社群文章。這一章換成我自己每天開著的四個 Mod，內容取自我的 Obsidian 工具筆記，路徑與設定照原文，包含沒做好的地方。四個裡有三個是自製（其中 obs-log-timer 是請 Claude 用內建的 plugin-authoring skill 產生，file-collision 由 subagent 完成），一個是 Anthropic 社群 marketplace 上的 next-steps。

Mod來源作用
obs-log-timer自製（請 Claude 代寫）每天 12:00、17:00 自動執行 /write-obs-log
herdr-watch自製狀態列顯示 herdr agent 計數、卡住提醒、/herdr 面板
file-collision自製（由 subagent 完成）別的 session 30 分鐘內寫過同一檔案時，寫入前詢問
next-steps社群 claude-community marketplace每回合結束後建議 3 個下一步 prompt

三個自製 Mod 放在C:\Users\porte\.claude\mods\ 底下，用 CLAUDE_CODE_PLUGIN_DIRS 載入（這個環境變數的定義與分隔符號見第 4 章）。我的設定如下，路徑用正斜線，多個 Mod 用 ; 分隔：

~/.claude/settings.json
"env": {
  "CLAUDE_CODE_PLUGIN_DIRS": "C:/Users/porte/.claude/mods/obs-log-timer;C:/Users/porte/.claude/mods/herdr-watch;C:/Users/porte/.claude/mods/file-collision"
}

obs-log-timer：定時排入工作日誌

我每天會把對話整理寫進 Obsidian 工作日誌，這個 Mod 把它變成定時自動執行：每分鐘看一次台北時間，12:00～12:09、17:00～17:09 各觸發一次，用 $.command.run({ command: 'write-obs-log' }) 排入指令。指令會等 session 閒置才執行，不會插進正在跑的回合。

💬

三個坑有兩個出自測試環境的規則：請 Claude 寫 Mod 時，測試要跟著一起寫，坑才會在你之前被踩到。

幾個刻意的設計：同一時段只送一次；載入當下如果已經在時段內就不送，避免重載時重送；-p、SDK 等非互動 session 不送；送出時跳 toast「obs-log-timer：12:00 排入 /write-obs-log」。檔案結構就是第 8 章的最小三檔加測試：

檔案內容
.claude-plugin/plugin.json名稱、版本 0.1.0、說明
hooks/hooks.json內容只有一行，見下方
hooks/register.tssession.start 起 $.clock.every(60_000) 計時器
tests/register.test.ts11:58 到 12:01 送一次、12:21 不重送、17:01 送第二次；非互動不送
hooks/hooks.json
{ "modules": ["./register.ts"] }

建立與驗證的方式一致：先用提示語請 Claude 代寫，再用 claude plugin validate 與 claude plugin test 檢查（這個 Mod 有 2 個測試）。下面是我當初使用的提示語，以及驗證指令：

建立 obs-log-timer 的提示語
/plugin-authoring 做一個 mod：每天 12:00 和 17:00（台北時間），在執行中的 Claude Code session 閒置時，自動執行 /write-obs-log，把這段對話整理寫入 Obsidian 工作日誌。非互動 session 不送，同一時段只送一次，並寫測試。
驗證與測試
claude plugin validate C:/Users/porte/.claude/mods/obs-log-timer
claude plugin test C:/Users/porte/.claude/mods/obs-log-timer

它有兩個限制我就直接接受：只在當下有開著的 Claude Code session 觸發，那時沒開就跳過；開幾個 session 就各寫一段到當天日誌。

⚠️
開發時踩到的三個坑

其一，$.prompt.submit 不能送 / 開頭的文字，要執行 slash 指令得用 $.command.run({ command, args })。其二，測試裡的 tier() 只接受 prepend、user、append、builtin。其三，測試裡的 ui.toast hook 要回傳 { value: undefined }，不能回 {}。這三條是開發過程中實際踩到的，第二、三條出自測試環境的型別與回傳值規則，所以建議一開始就要求 Claude 連測試一起寫。

herdr-watch：把 agent 狀態放進狀態列

herdr 是我用來同時管理多個 AI agent 的終端多工器。agent 一多，就常常有一個卡在等確認而我沒注意到。herdr-watch 用 wsl.exe -e bash -lc "herdr agent list"（唯讀）讀取所有 agent：/herdr 面板開著時每 20 秒讀一次，沒開時每 5 分鐘讀一次（這個頻率是 2026-10-12 調整的），打開面板當下立刻讀一次。

顯示分三處：狀態列像 herdr 14 · ⚙2 · ⚠1 卡住，讀取失敗時顯示 herdr ✗ 讀取失敗；agent 新變成 blocked 時跳一次 toast，持續卡住不重複提醒；/herdr 開側邊面板，blocked 紅色排最前、working 黃色、idle 灰色，列出名稱、workspace 與視窗標題。這部分的畫面技巧就是上一章的 band 與 pane。

它不花 token：只在本機執行指令，沒有呼叫模型也沒有連網，成本只有每次啟動 wsl.exe 的 CPU。測試有 4 個，包含輪詢間隔測試與一份真實 herdr 輸出的 fixture。每個開著的 session 各自輪詢，所以開得越多，啟動 wsl.exe 的次數也越多。之後要改，我沿用同一個提示語樣板：

修改 herdr-watch 的提示語樣板
/plugin-authoring 修改 C:\Users\porte\.claude\mods\herdr-watch：<需求>，更新測試並跑 claude plugin test。

file-collision：撞車警報

同時開兩三個 session 做事時，後面的 session 可能把前面剛改的檔案蓋掉。這個 Mod 的行為與第 13 章引用的 EP421 影片中的撞車警報相同：Edit、Write、NotebookEdit 成功後，把路徑、session 與時間記到 C:\Users\porte\.claude\mods-data\file-collision.json，所有 session 共用同一份；寫入前若發現別的 session 在 30 分鐘內寫過同一路徑，就跳 toast 並用 classic.PreToolUse 回傳 { ask }，彈出詢問框，並建議先重新 Read。

規則刻意保守：自己寫過的不算；超過 30 分鐘的紀錄自動清掉；Mod 本身出錯一律放行。它的限制我寫在筆記裡，這裡原樣列出：

  • 看不到你在編輯器手動做的編輯、herdr 裡其他 agent 的動作，也看不到 Bash 寫檔。
  • 兩個 session 同時寫入，可能漏記其中一筆。
  • 自動核准模式下，詢問框可能直接通過，這點我沒有實測。

最後一條值得多想一下：它是警報器，不是權限系統。真正需要擋的操作，仍然要靠 permission 規則，詳見第 15 章。

next-steps：唯一裝別人的

四個裡面只有 next-steps 不是我寫的。它每回合結束後，在輸入框上方列出最多 3 個建議的下一步 prompt；按 1、2、3 把建議填進輸入框，自己按 Enter 才送出，0 關掉，Tab 採用第一個（顯示為灰色提示字）。它不會自己送出 prompt，也只在終端機畫面顯示。EP421 提到作者是 Claude Code 團隊的工程師，並指出它放在 Anthropic 社群 plugin marketplace、預設未加入，所以要先加 marketplace 再安裝：

安裝 next-steps
claude plugin marketplace add anthropics/claude-plugins-community
claude plugin install next-steps@claude-community

裝完在 Claude Code 輸入 /reload-plugins 或重開。選填設定用 /plugin configure next-steps@claude-community，有兩個選項：minAnswerChars（回答至少多長才給建議）與 suggestSkills（建議裡要不要包含 skill 與 slash 指令）。不想用時停用，不必解除安裝：

停用與啟用
claude plugin disable next-steps@claude-community
claude plugin enable next-steps@claude-community

我沒有直接信任它，而是在 2026-10-12 先讀過原始碼。register.tsx 共 230 行，用到的 API 只有 $.command.list、$.model.fork、$.prompt.fill、$.prompt.suggest；沒有連網、沒有執行外部指令、沒有讀寫檔案。成本方面，每回合一次 $.model.fork，沿用對話快取，大約是一則短回覆的費用。這份審查紀錄的做法，就是第 16 章審查清單的縮小版。

延伸：把 next-steps 改成多選版

用了一陣子，我想要的是一次勾兩三個建議，合併成一個 prompt 再送。原版一次只能挑一個，設定裡也沒有多選的選項，所以我照第 7 章的做法做了一個自己的版本 next-steps-multi。它不是從零寫的，是從已安裝的 next-steps 1.0.0 複製來改：原作者是 Thariq Shihipar，授權是 MIT，所以我保留了原始的檔案說明；register.tsx 開頭標明「改自社群 next-steps 1.0.0，MIT」，plugin.json 的作者欄也標明改自 Thariq Shihipar 的 next-steps、採 MIT 授權。這是本書改編，不是原作者的版本，原版的行為請以原作者的說明為準。

操作方式：1、2、3 變成勾選與取消，畫面上每個建議前面多了 [ ] 與 [x]；按 4 把勾選的合併成一個 prompt，填進輸入框當草稿，自己按 Enter 才送出；0 照舊關掉。只勾一個就原樣填入，勾多個就編號成清單。有勾選且輸入框為空時，合併結果也會顯示為灰色提示字，按 Tab 可以採用。取消到沒有任何勾選時，灰字要清掉：引擎沒有清除灰字的 API，我試過兩種提議，空字串與單一空白都會讓 $.prompt.suggest 丟出 HooksError；最後改送零寬空白（U+200B），它顯示為空白，畫面上的灰字就消失了。這個做法的代價是：取消後若按 Tab，可能把這個看不見的字元填進輸入框，我還沒測過。程式的設計是：按 4 填入失敗時，清單會還原成原來的勾選狀態，讓你可以重試，而不是消失；這一段目前還沒有實測到（見下方）。

邏輯很短，我把它獨立成 hooks/merge.ts，測試才能直接測：

merge.ts：合併與限制
// hooks/merge.ts：獨立成檔的純函式，tests/ 直接測
export type Pick = { prompt: string }

export function isCommand(prompt: string): boolean {
  return prompt.startsWith('/')
}

export function canAdd(selected: readonly Pick[], candidate: Pick): boolean {
  if (selected.length === 0) return true
  return !isCommand(candidate.prompt) && selected.every(item => !isCommand(item.prompt))
}

export function mergePrompts(selected: readonly Pick[]): string {
  if (selected.length <= 1) return selected[0]?.prompt ?? ''
  return selected.map((item, index) => `${index + 1}. ${item.prompt}`).join('\n')
}

其中有一條是我自己加的規則：以 / 開頭的建議（例如 /code-review high）不能和別的合併。原因是指令後面接的文字會被當成它的參數，串在一起行為就變了，所以已有其他勾選時再勾指令型，或已勾指令型時再勾其他建議，都會跳出「指令型的建議只能單選，不能和其他建議合併」。若沒勾任何一個就按 4，會提示「先按 1／2／3 勾選要合併的建議」，輸入框不變。claude plugin test 的兩個測試涵蓋合併與限制的純函式：單選原樣、多選編號、沒選是空字串，以及指令型不能混合。

為什麼合併鍵是 4，不是 Enter

我原本想讓 Enter 負責合併，這樣和平常送出的手感一致；但官方型別檔（.claude-plugin/types/claude-code/index.d.ts）對 Button 的描述顯示，Enter 不能當作這個按鈕的 hotkey：

  • Button 的 hotkey 只接受一個數字或一個小寫字母，Enter 不是合法值。
  • 型別檔說，從輸入框觸發上方按鈕的 hotkey，限於空輸入框中的單一數字；小寫字母要在外掛區域取得焦點後才作為 hotkey 生效，例如按 ctrl+x tab 或點選該區域。
  • 型別檔說 Enter 會按下焦點所在的按鈕；它沒有把 Enter 定義為從輸入框觸發這排按鈕的 hotkey。

所以要從空輸入框直接用 Button 的 hotkey 觸發合併，我選數字鍵：1、2、3 用掉了，第四個數字 4 就給合併。這也和原版 0 關閉的習慣在同一排，不用換手勢。附帶的好處是 4 不會和 Enter 的「送出」混淆：合併只是把草稿填好，送出仍然是你自己按 Enter，符合原版「不替你送出 prompt」的原則。

這條限制是我讀型別檔得到的，我沒有逐一驗證每種焦點狀態下 Enter 的實際行為。

要試用時，先停用原版（兩個 Mod 會搶同一排數字鍵），再用 --plugin-dir 載入：

停用原版、載入多選版
claude plugin disable next-steps@claude-community
claude --plugin-dir C:/Users/porte/.claude/mods/next-steps-multi

claude plugin validate 列出的 hooks: 與 calls: 與原版完全相同，沒有多用任何 API。驗證時它還擋下一個錯誤：我新取的變數名 next 和引擎的 next（交給下一個處理者）同名，會被判定為遮蔽（shadowed），改名後才通過。這是第 10 章講的驗證在實際改 Mod 時發揮的作用。

實測結果（2026-10-16）

我在 WSL 的 Claude Code 2.1.301 開一個全新的 session，用 --plugin-dir 載入 next-steps-multi；原版 next-steps 在 Windows 端先停用（WSL 端本來就沒啟用）。請 Claude 用三句話說明 git 並建議後續主題，回合結束後輸入框上方出現三個建議，下面依序是我按鍵的結果：

操作結果
回合結束列出三個建議，每個前面是 [ ]，多出「4: 合併填入（已選 0）」；輸入框的灰色提示字是第一個建議
按 1第一個變 [x]，「已選」變 1；灰色提示字仍是第一個建議
再按 3第三個也變 [x]，「已選」變 2；灰色提示字變成「1. …」換行「2. …」的合併結果
再按 3取消勾選，回到只勾第一個
勾 1 與 3 後按 Tab合併結果填進輸入框；再打一個字會接在後面，確認是真的文字，不是灰色提示。建議清單沒有消失
清空輸入框後按 4建議清單收起，合併結果填進輸入框當草稿，沒有送出，Claude 沒有開始回答

實測也有兩點和我原本的預期不同：用 Tab 採用時，建議清單不會自動收起；這組操作中，按 4 才讓清單收起（0 也能關閉）。另外輸入框裡有字的時候，按數字鍵只會打出數字，不會勾選，這和原版一樣，所以要先清空輸入框。

這次沒有測的：沒勾任何一個就按 4 的提示、勾到指令型建議時的拒絕提示（測試只涵蓋邏輯，沒有在畫面上看過），以及 Enter 在各種焦點狀態下的行為。這個 session 是在 WSL 跑的，沒有在 Windows 的 Claude Code 上重做。

之後又做了兩次實測，驗證修正後的灰字行為。確定的部分：外掛的 prompt.suggest 提議會被引擎接受並顯示，按 3 後灰字會換成第三個建議的內容，按 Tab 採用的是外掛的提議，清單仍然留著；取消到沒有勾選後，灰字清掉。未測到的：「按 4 填入失敗時清單還原」。正常操作下很難讓 $.prompt.fill 失敗，我沒有找到可重現的方法，所以只通過了 claude plugin validate，這段邏輯目前沒有實測。

ℹ️
VS Code 擴充套件的對話面板看不到 Mod 介面

我在 2026-10-12 實測：狀態列、toast、pane 只出現在終端機與桌面版的 Code 分頁。VS Code 對話面板裡 hook 照跑（obs-log-timer 照樣執行，file-collision 的詢問框是引擎功能），但看不到 Mod 畫的東西。要看 herdr-watch 請在終端機開 claude。

回頭看這四個，有幾條共通的心得。需求都來自「我每天重複做的事」：寫日誌、盯 agent、避免覆蓋、決定下一步。能不連網、不執行外部指令就不做：只有 herdr-watch 會啟動外部程式（唯讀的 herdr agent list），並且我知道它做了什麼。每個自製 Mod 都有測試。最後，裝別人的 Mod 前先讀它用了哪些 API，這個習慣花不到五分鐘。

💬

230 行原始碼、4 個 API、不到五分鐘：我敢裝 next-steps，是因為先讀過，不是因為它放在社群 marketplace 上。

小結與下一章

這四個 Mod 加起來碰過排程、外部程序、共用檔案與模型呼叫，已經涵蓋了 Mod 能力範圍裡風險最高的幾種。它們能這樣放心地跑，是因為我知道每一個做了什麼，不是因為 Mod 有什麼保護機制。下一章回到這個前提：Mod 沒有沙箱，權限跟你一樣。我們會整理官方文件怎麼說、安全研究者展示了什麼，並區分哪些是事實、哪些只是推論。
