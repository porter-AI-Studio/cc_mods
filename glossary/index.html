核心概念

ModClaude Code 內的外掛前言第 1 章第 2 章第 6 章

官方文件的定義：Mod 是一個會改變 Claude Code 外觀與行為的 plugin，由 JavaScript 或 TypeScript 的事件處理函式組成；事件發生時 Claude Code 呼叫函式，函式可以觀察、改寫或接管事件。

Mods 隨 Claude Code 2.1.287 於 2026 年 10 月 1 日上線（Desktop app 從 2.1.286 起支援）。因為跑在 Claude Code 程序內部，它能畫可操作的介面、重繪 Claude Code 自己畫的部分、介入 tool call 或請求、新增立即執行的 /command，並在 hook 之間共享資料。這些是 skill、MCP 伺服器與 settings hook 做不到的。代價是 Mod 沒有沙箱，以你的權限執行。

實務提示：GitHub 上的 0xDarkMatter/claude-mods 是 skills 與 agents 的工具集，與這個原生 Mods 功能無關，別搞混（第 1、6 章）。
Plugin發行與打包的單位第 2 章第 4 章第 10 章

第 2 章的說法：plugin 是「打包與發行的單位」，不是與 skill、MCP 並列的功能；Mod 本身就是一種 plugin，一個 plugin 可同時放 skills、settings hooks、Mod、commands、agents 與 MCP 伺服器。

hooks/hooks.json 裡用 modules 指向程式碼，同一個檔案也可以照舊放 settings hooks。Mod 以 plugin 的形式安裝，所以 marketplace、安裝範圍與更新方式都與一般 plugin 相同。官方管理文件寫明 settings hooks 與 Mod 並存，沒有任何一項被棄用。

實務提示：要把 Mod 給別人用，就是發行 plugin（第 10 章依對象選分享方式）。
Hook（Mod 的 hook）Mod 的事件處理函式第 1 章第 3 章

本書談到 Mod 時，hook 指 Mod 的事件處理函式（官方文件的用法）；它掛在事件上，每個 hook 收到 $、e、next 三個參數。

Mod 的 hook 是在 Claude Code 程序裡面執行的函式；settings hook 則在 Claude Code 外面以 shell 指令、HTTP 請求或 prompt 執行。這個執行位置的差別，決定了 Mod 能畫介面、保留記憶體狀態、並在同一個函式裡 await next(e) 看到事件前後。

實務提示：讀到「hook」時先分清是 Mod 的 hook 還是 settings hook，兩者能力與審查方式都不同。
Settings hook設定檔裡的既有 hooks第 1 章第 2 章第 11 章

寫在設定檔裡、以 shell 指令、HTTP 請求或 prompt 形式執行的既有 hooks；官方把兩者都叫 hooks，文件刻意用「settings hook」區分。

它不能在介面上畫東西，command 型每次都是新程序，要保留狀態得自己寫檔；PreToolUse 與 PostToolUse 要分成兩個事件、兩支腳本。Mod 並沒有取代它。順序上，managed settings 的 PreToolUse 比任何 Mod 的 tool.call 先執行，擋下即定案；其他設定檔與 plugin 的 PreToolUse 則在最後一個 Mod 呼叫 next 之後才執行。

實務提示：只是要阻擋、放行或記錄，而且已有現成腳本，用 settings hook 就夠，不必寫 Mod（第 2 章「先用最輕的工具」）。
Hooks module 與 registerMod 的進入點第 1 章第 3 章第 8 章

hooks module 是 Mod 的程式碼檔，匯出 register(on, options)；Claude Code 載入 plugin 時呼叫 register 一次，在裡面呼叫 on 註冊 hook。

一個 Mod 是三個必要檔案：.claude-plugin/plugin.json（manifest）、hooks/hooks.json（用 modules 指向 hooks module，缺了它就只是普通 plugin）、以及 hooks module。副檔名可為 .js、.mjs、.cjs、.jsx、.ts、.mts、.cts、.tsx，內容必須是 ES module，不需要 Node.js、打包工具或建置步驟。模組載入後常駐 session，頂層變數一直活著，但熱重載時會重跑 register 而歸零。

實務提示：要跨重載保留的值，放進 $.state（整個 session）或 $.store（跨 session），不要放模組變數（第 8、9 章）。

事件與處理方式

Event 與 matcher事件與比對條件第 3 章第 9 章

Claude Code 在每個關鍵時刻發出一個事件，hook 掛在事件上；on 的第二個參數 matcher 是物件，欄位與事件欄位全部符合時 hook 才執行，值可為字串、陣列或正規表示式。

事件名稱是小寫點分格式的字串，如 tool.call、ui.render、prompt.submit；每個 settings hook 事件有對應的 classic. 事件，mods API 的每個方法（如 fs.read、ui.open）本身也是事件。'classic.*' 比對所有 settings hook 事件，'*' 比對除了 telemetry 以外的所有事件。同一事件沒有 matcher 就不能註冊兩次，否則模組載入失敗。第 3 章指出預覽期文章曾用大寫（如 Tool.Call）等稱呼，事件名稱拼錯時 validate 會報 is not an event。

實務提示：事件名稱必須是字串常值，用變數或迴圈靜態分析會失敗；每個事件可回傳的結構不同，要查 reference 的「A hook can return」欄。
$、e、nexthook 的三個參數第 3 章第 8 章

$ 是 mods API，hook 對外做事只能透過它；e 是事件輸入，深度凍結的純資料；next 是下一個處理者，同一事件上的 hook 串成 middleware 鏈，鏈末端才是 Claude Code 自己的行為。

e 直接指派欄位會丟出錯誤，要修改就傳一份副本給 next。$ 的呼叫要寫完整（如 $.fs.read('notes.md')），不能把 $.ui 指派給變數或解構；沒有 Node 也沒有 DOM，檔案用 $.fs、程序用 $.process、網路用 $.http、計時用 $.clock、跨 session 儲存用 $.store。

實務提示：「沒有 Node、沒有 DOM」限制的是 API 的取得方式，不是權限（第 3 章）。
觀察／改寫／接管observe／rewrite／answer第 1 章第 3 章第 8 章第 12 章

hook 如何使用 next 決定處理方式：回傳 next(e) 是觀察；把修改過的副本傳給 next 是改寫；不呼叫 next 而直接回傳結果是接管（回答）。

接管時鏈被截斷，後面的 Mod 與 Claude Code 自己的行為都不會執行，例如 tool.call 回 deny，Claude 讀到的是 deny 的文字。每個事件的回傳結構不同：tool.call 可回 deny 或 result，prompt.submit 則是 drop。想在事件之後做事就 await next(e)。守門 hook 要在呼叫 next 之前就決定，因為 next 一旦執行，指令就已經跑了（第 12 章）。

實務提示：不能把一個事件的拒絕格式搬去另一個事件，要查 reference。
Hook 鏈順序prepend／user／append第 3 章第 11 章

同一事件上的 hook 組成中介鏈，第一個 Mod 在最外層：先看到事件、最後看到結果，並決定後面的 Mod 要不要執行；後面的 Mod 無法阻止前面的看到事件。

順序依來源：內建守衛 sec-default@builtin、組織以 prependPlugins 列出的 Mod 及其他算作組織的 Mod；然後是你安裝的 Mod；然後是組織以 appendPlugins 列出的 Mod；最後是其他內建 Mod。你安裝的 Mod 之間，一個 Mod 排在它於 manifest 的 dependencies 列出的 Mod 之前（第 3 章）；第 11 章的說法是宣告在 dependencies 的 Mod 排在依賴它的 Mod 後面，方向一致；同一模組內依 register 呼叫 on 的順序。鏈是串行的，慢工作不要塞進鏈裡。

實務提示：順序看的是設定中的位置，不是安裝的先後；一旦 managed settings 定義了 prependPlugins，那份清單就是整個 prepend 層（第 11 章）。
.catch 守門（fail closed）失敗時拒絕的錯誤處理第 2 章第 3 章第 8 章第 11 章第 12 章第 15 章

hook 丟例外、逾時或回傳錯誤結構時，在呼叫 next 之前失敗會被略過，守門 hook 因此等於放行；on 回傳的註冊物件有 .catch(handler)，可改成失敗時拒絕。

next.called 讓處理函式分辨失敗前有沒有呼叫過 next，next.error.kind 說明原因（如 throw、timeout，或 v2.1.292 以上的 re-entry）。一個 hook 本身有 10 秒時限，但 .catch 處理函式只有 1 秒。純觀察的 Mod（如計量條）則應失敗時放行：.catch(($, e, next) => next(e))。tool.check 與 plugin.register 例外：在 next 之後回傳的拒絕仍然有效。validate 會為每個可能拒絕動作的 hook 多印一行，標出有沒有 .catch。

實務提示：守門 Mod 沒有備援就得接受它出錯時會放行；真正不能放行的操作交給 permission 規則或 managed settings（第 15 章作者判斷）。
Noun contractmod 之間的介面契約第 5 章第 11 章

mods API 的命名空間（$.fs、$.ui 等）內部稱為 noun；新增 noun 的 Mod 把型別放在 types/index.d.ts，這份宣告檔就是合約，是該 noun 唯一的宣告。

Mod 可掛 engine.create 回傳多了新 noun 的 API；呼叫別人的 noun 要讀同一份檔案、不要複製；依賴別人 noun 的 plugin 在 plugin.json 用 dependencies 宣告。內建 telemetry 加入 $.telemetry，diff 與 agents-md 呼叫它；telemetry 不在場時那些呼叫被無聲丟棄。第 11 章自述素材有限，主要來自內建 Mod 的 README，且該 README 自己標示 early access。

實務提示：提供者不在時要有退路（diff 沒有 $.telemetry 就只是丟掉那些資料列）；測試時先放一個 provider。

介面與 API

Render site介面繪製位置第 3 章第 9 章

Claude Code 畫面上每個可擴充的位置；每個 site 對應一次 ui.render 事件，e.component 是 site 名稱，e.props 是它的資料，e.surface 是 terminal 或 desktop。

常用的有 AbovePrompt、Pane、Spinner、UserMessage、AssistantMessage、ToolUse 等。元素要用 $.ui.resolve(e) 取得當下 surface 能畫的建構函式；Svg 只有桌面版畫得出來，Raster 與 Image 只有終端機。hasSurvey 為真時是問卷要用這個位置，讓出去；沒東西可畫就回 next(e)。

實務提示：畫面只在終端機與 Desktop 的 Code 分頁看得到；VS Code 擴充套件面板與 claude -p 不畫（第 3、9 章）。
Band 與 Pane輸入框上方橫帶與側邊面板第 1 章第 9 章第 12 章第 13 章

band 是輸入框上方的細帶（render site 為 AbovePrompt），pane 是開在對話記錄旁邊的側邊面板（Pane，由 $.ui.open 開啟）；兩者都可以放分頁、按鈕與文字輸入框。

第 12 章引用的 10 月 6 日目錄掃描指出 41% 的 Mod 畫在色帶、40% 開面板。面板若沒被使用者主動要求，要寬 144 欄才會自動開（使用者開過一次後降到 110 欄），空間不夠時 $.ui.open 回傳的 isPlaced 為 false，這時改畫在色帶上。色帶是共用的，要先 await next(e)，把結果放進自己的 Box，否則會蓋掉其他 Mod 的那一行。

實務提示：寬度讀 e.props.bodyColumns，dock 型 pane 的可用列數是 e.props.scroll.bodyRows。
$.state 與 $.store響應式狀態與跨 session 儲存第 8 章第 12 章第 13 章

$.state 是響應式狀態，整個 session 有效，熱重載不歸零；$.store 是本機所有 session 共用的 JSON 鍵值儲存，全部合計 4 MiB。

畫面要讀的值放 $.state 而不是模組變數；/clear 會重來，要跨 /clear 保留就在 session.end 寫進 $.store。$.state 的每個值要在 types/index.d.ts 宣告，否則驗證不過。$.fs.write 不是原子操作，多個 session 都會改的資料請放 $.store。

實務提示：待辦、快取起算時間這類跨 session 共用的資料，用 $.store 比自己寫 JSON 檔穩（第 13 章）。
$.model.complete 與 $.model.fork替 Mod 另外叫一次模型（分叉）第 9 章第 14 章第 16 章

Mod 可自己向模型發小請求；complete 用你傳的 model、只含你的 prompt、不含 CLAUDE.md；fork 用工作階段目前的模型與 system prompt、帶到目前為止的對話。

fork 會重送對話最後一次請求，所以只要 prompt cache 還活著，大部分內容由快取提供；next-steps 每回合一次 $.model.fork，成本約一則短回覆。兩者費用都算在使用者自己的方案、API key 或雲端供應商。Claude API 失敗時呼叫不會 reject，要先看 r.isAnswered，false 時原因在 r.reason。區塊陣列加 cache: true 需 v2.1.292 以上。

實務提示：在 validate 的 calls: 出現 $.model.complete 代表會花你的額度；每回合會呼叫幾次要問清楚（第 16 章）。
指令（$.command.register）給使用者的 slash command第 1 章第 7 章第 9 章第 10 章第 12 章第 14 章

在 session.start hook 用 $.command.register 登記，再用 matcher 限定只處理該名稱的 command.run；指令直接執行你的函式，不經過 Claude 的回合。

指令名稱只能用英數字、_ 與 -，最長 64 字元；撞到內建指令時 register 會丟錯，所以登記放在 hook 最後或包 try 與 catch。第 12 章記錄兩種說法：教學原文說指令在 Claude 忙碌時也會立即執行；官方 API 文件則要求登記時加 immediate: true。要讓 Claude 而不是使用者呼叫，改用 $.tool.register。

實務提示：$.prompt.submit 不能送 / 開頭的文字，要執行 slash 指令得用 $.command.run（第 7、10、14 章作者實測記錄，非官方列表）。

安裝、驗證與開發工具

claude plugin validate靜態驗證與審查指令第 4 章第 6 章第 8 章第 10 章第 15 章

不執行 Mod、不開 session，只讀 manifest 並對 hooks module 原始碼做靜態分析，印出它掛了哪些事件（hooks:，括號內是 matcher）與呼叫了哪些 mods API（calls:）。

另有 env reads:、env writes:、state reads: 與「gating hook without .catch」等行。--strict 把警告當錯誤，--json 輸出機器可讀報告，兩者適合 CI。靜態分析限制：API 呼叫寫完整、事件名稱用字串常值、只用 ES module import、只能相對路徑 import（唯一裸 import 是 claude-code）。第 15 章指出它說的是「會呼叫什麼」不是「會做什麼」。

實務提示：validate 不是安全稽核：它是審查的起點，不是通過證明；出現 $.process、$.http、$.fs.write、$.env、$.model 的地方還要讀原始碼（第 10、15 章）。
claude plugin testMod 測試指令第 6 章第 10 章

在 Mod 資料夾執行，會跑底下所有檔名以 .test.ts 或 .test.tsx 結尾的檔案，不需要登入、網路或 session；有測試失敗時以狀態碼 1 結束。

測試會觸發 hook 處理的事件再檢查結果；每個測試預設 5 秒，可設 timeoutMs。畫面類 Mod 用 $.ui.mount 掛起 render site 再用 find 找元素；Text 元素沒有 key，要用文字去找。內建 Mod 附有測試，diff 用 mock.clock(on)、mock.store、mock.env 模擬時間、儲存與環境變數。

實務提示：宣稱通過 validate --strict 與原生測試的合集可以自己在全新 clone 上重跑（第 6 章）；沒有測試的 Mod，品質訊號少一個。
Stand-in hook測試中的代理 hook第 10 章第 12 章

測試套件底下沒有真正的 Claude Code，所以在你的 Mod 之後用 on 註冊 stand-in hook 扮演 Claude Code，例如 on('tool.call', () => ({ result: 'ok' })) 代替回答工具呼叫。

沒人回答的呼叫會丟錯：nothing beneath the plugins answers。stand-in 要在測試的第一個 $ 呼叫之前註冊，否則報 on("tool.call") after the test first called $；替 $ 方法做的 stand-in 要回 { value: ... }，裸結果會被拒絕。

實務提示：作者的守門器第一次執行就因為順序錯誤失敗（第 12 章）。
--plugin-dir 與 CLAUDE_CODE_PLUGIN_DIRS載入本機 Mod 目錄第 4 章第 7 章第 10 章

--plugin-dir 把 plugin 目錄載入單次 session，不必先裝進 marketplace；CLAUDE_CODE_PLUGIN_DIRS 環境變數效果等同，可設在環境變數或 ~/.claude/settings.json 的 env。

路徑要用絕對路徑，多個目錄之間用 : 分隔，Windows 用 ;。Desktop app 不能帶旗標，專案層級設定會被忽略。用 --plugin-dir 載入的目錄會被監看，存檔就熱重載 hooks module 並重跑 register；長時間非互動 session 可設 CLAUDE_CODE_PLUGIN_DIR_WATCH=1。Claude Code 依版本快取已安裝的 plugin，開發時一直用 --plugin-dir，改完要調高版本號才會更新已安裝副本。

實務提示：經 --plugin-dir 載入的 Mod 不經 marketplace；要和別人共用仍走 marketplace（第 4 章）。
plugin-authoringClaude 代寫 Mod 的 skill第 4 章第 5 章第 7 章

內建 skill，告訴 Claude 三件事：Mod 該寫在哪裡、你這個版本有哪些事件與方法、以及 Mod 怎麼被載入；可輸入 /plugin-authoring 自己載入。

由 cc-plugin-plugin-authoring 帶進來，只有 skill、沒有 Mod 程式碼，可在 /plugin 停用。代寫流程：逐檔核准（~/.claude 是受保護路徑）、啟用熱重載（Enable hot reloading for this session?）、用 /plugin 確認載入。Claude 寫的 Mod 只在寫它的 session 載入，session 的 mods 資料夾超過 cleanupPeriodDays 會被刪，要保存須複製目錄。

實務提示：代寫不等於免審：validate、test 與讀程式碼一個都不能省（第 7 章）。
Marketplaceplugin 來源目錄第 4 章第 6 章第 10 章第 14 章第 16 章

Mod 以 plugin 形式發行，安裝格式是 plugin 名稱、@、marketplace 名稱；marketplace 只需在 .claude-plugin/ 放一個 marketplace.json，推到 GitHub 即成立。

官方沒有只收 Mod 的圖庫；第 6 章列出的社群目錄有 claude-mods.com、awesome-claude-code-mods 與 claudemods.ai，其中只有 awesome 清單列出每個 Mod 的事件、API 與觸及範圍。從 shell 安裝時若 session 已開著，要在該 session 執行 /reload-plugins。第 14 章的 next-steps 來自預設未加入的 claude-community marketplace。

實務提示：marketplace 條目可用 ref 加 40 字元 commit sha 固定第三方 plugin（第 16 章）。
--safe-mode 與 disableAllHooks緊急關閉 Mod第 4 章第 6 章第 16 章

官方依範圍分三層關閉：在 /plugin 停用單一 Mod；claude --safe-mode 讓單次 session 不載入所有已安裝 Mod（同時停用其他客製設定）；~/.claude/settings.json 設 "disableAllHooks": true 每次 session 都停。

disableAllHooks 會連 settings hooks 與自訂狀態列一併停止，組織管理的部分照常；停掉的只是 Mod，plugin 裡的 skills、commands、agents 與 MCP 仍載入。這些設定與 --bare 都停不了內建 Mod。CLAUDE_CODE_ENABLE_FUNCTION_HOOKS 是預覽期變數，2.1.287 以後會被忽略，設成 0 也關不掉 Mods。

實務提示：懷疑某個 Mod 造成問題，用 --safe-mode 開乾淨 session 對照最快；但注意它也會停掉組織的政策 Mod（第 16 章）。

內建 Mod 與組織管控

Managed settings組織管理設定第 4 章第 15 章第 16 章

管理員決定 Mod 是否執行、執行哪些的設定來源；送達方式有 admin console 的 server-managed、MDM、本機 managed-settings.json 三種。

官方說預設同一台機器只套用其中一種，順序是 server-managed、MDM、檔案，取第一個有送出政策鍵的來源；server-managed 送了任何不相關的鍵，MDM 與檔案的 plugin 鍵就被忽略，除非 managedSourcesBehavior 設為 "merge"。多數管控鍵只有放在 managed settings 才算數，放在使用者、專案、本機設定檔或 --settings 都沒有效果。

實務提示：第一步先確認 managed settings 真的送到每台機器；用 --plugin-dir 載入一個 Mod 看是否被拒絕來驗證（第 16 章）。
sec-default內建守衛 Mod第 3 章第 5 章第 15 章第 16 章

內建守衛 sec-default@builtin（在 /plugin 與 debug log 叫 cc-plugin-sec-default）；在使用者安裝的所有 Mod 之前載入，使用者無法關掉，保護組織管理的東西。

載入條件是機器上有 managed settings，或使用者以 Team、Enterprise 方案登入；用 API key 或 Bedrock、Google Cloud、Foundry 的使用者只有在有 managed settings 時才有。保護範圍是 managed hooks、系統提示、managed CLAUDE.md 與指示、設定讀取、managed MCP 工具與說明，官方說其餘都允許。README 把動作歸納為 next.to(e, "append") 越過 user 層、依名稱拒絕、或原樣放行。它自己的成本是每次工具呼叫都跑 tool.check 鏈，盲區是被擋下的 ask 仍可被使用者的 classic PermissionRequest hook 回答，要靠 allowManagedHooksOnly。

實務提示：沒有 managed settings 的個人電腦可能不在保護範圍內，只靠自己審查（第 15 章）。
allowManagedModsOnly只允許組織與內建 Mod第 4 章第 5 章第 16 章

放在 managed settings 的 pluginConfigs 下（守衛上）的選項：使用者安裝的、--plugin-dir 載入的、自己 mods 資料夾裡的，以及 Claude 在 session 裡代寫的 Mod，hooks 一律不執行。

組織自己的 Mod 與內建 Mod 照常運作，使用者設定檔的 settings hooks、狀態列與 /goal 不受影響；守衛只讀 managed settings 的這個值。要被視為「組織的 Mod」須同時符合三個條件：managed 的 enabledPlugins 為 true、marketplace 以絕對路徑指向機器上的目錄、marketplace 以相對路徑列出該 plugin；從 GitHub、git、URL、npm 複製到快取的一律算使用者的。相關的 allowManagedHooksOnly 範圍更廣，也擋使用者 settings 檔裡的 hook。

實務提示：它是 Mod 層級的「全關」；內建 Mod 不受影響，連你自己的 managed hook 也一起關的是 disableAllHooks（第 16 章）。
allowModsToOverrideDenyRules允許 Mod 推翻 deny 規則第 5 章第 12 章第 15 章

守衛的另一個選項，預設關閉，只有字面上的 true 才算數；守衛載入且未開它時，使用者的 Mod 不能核准被 deny 規則拒絕的呼叫（README 稱 Deny rules hold）。

背景是在 tool.check 上任何 hook 都能回答任何判決，一個回 decision: "allow" 的 Mod 連 deny 規則也一起放行。守衛在位時會再跑一次不含 user 層的鏈，兩次以較嚴格者為準。受保護的不只 deny，還包括有來源的 ask。第 15 章補充：在沒有守衛的情境（例如個人 Pro、Max 訂閱，或 API key 加沒有 managed settings 的機器），Mod 可以核准被 deny 規則拒絕的呼叫。

實務提示：deny 規則約束的是 Claude 發出的 tool call，Mod 自己呼叫 $.fs.read 不在規則範圍內（第 15 章）。
prependPlugins 與 appendPlugins組織的前置與後置 Mod第 3 章第 11 章第 16 章

managed settings 中列出組織 Mod 的兩個清單：prependPlugins 排在使用者 Mod 之前（外層），appendPlugins 排在之後。

「只用自己的政策 Mod 檢查其他 Mod」的做法是安裝自有 Mod，並與 sec-default@builtin 一起列入 prependPlugins；一旦定義了 prependPlugins，那份清單就是整個 prepend 層，要讓內建守衛載入就得把它寫進去。外層的 Mod 可以觀察、改寫或拒絕內層的 mods API 呼叫，內層不能反過來。

實務提示：從 GitHub、git、URL、npm 複製到快取的 plugin 算使用者的，prependPlugins 會略過（第 16 章）。
disableSideloadFlags封鎖旁路載入旗標第 16 章

啟動時拒絕 --plugin-dir 與 --plugin-url，並讓 Claude 在對話中寫的 Mod 無法載入，同時也拒絕 --agents 與 --mcp-config；須放在 managed settings 才算數。

與 marketplace 白名單（strictKnownMarketplaces，別名 allowedMarketplaces）搭配，才能達到「只有白名單內 marketplace 的 Mod」；strictKnownMarketplaces 本身擋不了 --plugin-dir。blockedMarketplaces 是黑名單且優先檢查，兩者檢查的是 marketplace 來源，不是裡面的單一 plugin。空陣列會鎖掉所有來源，包含官方 marketplace。

實務提示：它只決定能從哪裡裝，不管載入後的行為（第 16 章管控層級表）。
政策 Mod組織自寫的審查 Mod第 11 章第 16 章

當需要「允許某些人的 Mod、拒絕另一些」或「記錄 Mod 做了什麼」時自寫的 Mod；它在每個 Mod 載入前收到 plugin.register 事件，e.uses 就是 validate 印出的清單，可用 refuse 擋掉。

它也能用 API 呼叫名稱（如 fs.write）攔截所有 Mod 的對應呼叫。失敗行為是重點：檢查 hook 丟例外或逾時會被略過，檢查就變成放行，要加 .catch 改成失敗時拒絕。官方也說明：背景 worker 當掉三次，Claude Code 會卸載所有非內建 Mod（含政策 Mod）；--safe-mode 也會停掉。相對地守衛本身是失敗即拒絕：讀不到 managed settings 就拒絕所有使用者的 Mod。

實務提示：作者判斷：政策 Mod 是補強工具，不是唯一的防線；不能失手的限制仍用 managed settings 的鍵做。
agents-md內建的 AGENTS.md 載入 Mod第 1 章第 5 章

內建 Mod（顯示名稱 cc-plugin-agents-md），讓 Claude Code 讀 AGENTS.md，方式與讀 CLAUDE.md 一致；選項 instructionFiles 有四個值。

四個值：claude-md（只載入 CLAUDE.md）、claude-md-or-agents-md（預設，專案沒有 CLAUDE.md 才載入 AGENTS.md）、claude-md-and-agents-md（兩者都載入）、managed-only（只留組織的 managed CLAUDE.md 與引擎的 memory）。選項在 /config 的「Project instructions」列切換，或寫在使用者設定、--settings 或 managed settings，專案的 .claude/settings.json 不會被讀。第三方報導：2026 年 9 月 23 日有人發現設了 DISABLE_TELEMETRY=1 等變數會讓它無聲不讀 AGENTS.md（受遠端 feature flag 控制），維護者說 v2.1.281 同日修正；這是部落格與 Hacker News 的說法，非官方公告。並陳：agents-md 的 README 範例設定鍵是 agents-md@builtin，官方 overview 表格的顯示名稱是 cc-plugin-agents-md，sec-default 的設定鍵則是 cc-plugin-sec-default@builtin，兩處寫法不一致。

實務提示：官方說名稱以 /plugin 實際顯示為準；設定沒生效先確認鍵名，並用不常見字詞（如 PERIWINKLE）驗證指令確實被載入，要問兩次。

安全與審查

Mod 沒有沙箱No sandbox第 1 章第 3 章第 15 章第 16 章

官方文件的原話：Mod 是以你的權限執行的程式碼，可讀寫檔案、啟動程序、發網路請求，所以只該安裝來自信任作者與 marketplace 的 Mod；沒有任何一項管控會把 Mod 關進沙箱。

就算開了 Claude Code 的 sandboxing，沙箱隔離的是 Claude 執行的 Bash 指令，Mod 啟動的程序在沙箱之外。Mod 可重畫大部分介面但不能改權限提示本身，不過仍可在提示出現前核准或拒絕呼叫。Mod 到達外部只有一條路 $ API，每次呼叫本身都是事件，Pebblous 稱之為「咽喉點而非隔離」（Pebblous 的詮釋，非官方用語）。網路政策只涵蓋 $.http.fetch，不涵蓋 $.process.run 啟動的程式。

實務提示：管控決定誰能載入，審查才決定載入的東西可不可信；即使只放行組織自己的 Mod，它仍有使用者的全部權限（第 16 章）。
觸及範圍Reach第 6 章第 12 章第 13 章

第 6 章引用 awesome 清單掃描的說法：一個 Mod 能碰到什麼的足跡（只繪圖與記憶、讀檔、寫檔／跑程序／驅動 Claude、連網），比星數更有用；它只是足跡，不是定罪。

文章引用統計區塊日期 2026-09-17（對應 Claude Code 2.1.274）：72 個 Mod 中，只需繪圖與記憶的 20 個、會讀檔的 6 個、會寫檔／跑程序／驅動 Claude 的 32 個、會連網的 14 個。並陳：另一篇指南（StationX）把同一個目錄描述為 10 月 4 日重掃收錄 1,740 個 Mod，量級差很多，素材沒說明口徑是否相同，本書只引用趨勢。第 12、13 章另引用 10 月 6 日掃描的 2,690／2,692 個公開 Mod，也都不是官方統計。

實務提示：要問的是觸及範圍和工作是否相稱：只畫狀態列的 Mod 若同時在啟動程序，就值得問為什麼（第 6 章）。
來源標示官方說的／研究者展示的／作者判斷前言第 15 章第 16 章

本書的來源紀律：官方文件說的、第三方與研究者展示的、作者判斷與實測，三者分開標示；說法矛盾時並陳並附出處與日期，不替讀者擇一。

第 15 章把內容分成「官方文件說的」「研究者展示的」「作者推論」；第 16 章標「作者判斷」的部分不是官方建議。第 15 章的 Pluto Security 測試（2026 年 9 月 22 日發表）針對 v2.1.274 預覽期實作，作者自己也註明可能在正式版前改變，書中未在目前版本重現。另有書中並陳的矛盾：CVE-2025-59536，hackmag 說是 MCP 自動核准繞過，MintMCP 說是 SessionStart hook 的遠端程式碼執行，Anthropic 的 GitHub 公告則說是信任對話框出現前可能執行專案程式碼；撤銷是否立即生效，agentpatterns.ai 說要等下次 refresh，官方管理文件說 session 啟動時對已安裝 plugin 再檢查一次。第 16 章建議自行實測。
