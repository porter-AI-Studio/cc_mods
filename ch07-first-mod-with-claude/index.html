第 7 章 · Part 3：開發自己的 Mod

第一個 Mod：請 Claude 代寫

用一句話描述，讓 Claude 在 session 裡寫、載入、再替你改

前兩章你看到的是別人寫好的 Mod。從這一章起換你動手。官方文件對「做一個 Mod」給了兩條路：請 Claude 代寫，或自己照教學寫三個檔案。這一章走第一條，下一章再走第二條。順序不是隨便排的：先看 Claude 產出什麼，你才知道手寫時每個檔案該長什麼樣。

前提是 Claude Code v2.1.287 以上；在終端機用 claude --version 確認。Desktop 的 Code 分頁要 v2.1.286 以上，這在 Mods overview 有明列。

plugin-authoring：Claude 為什麼知道怎麼寫 Mod

Claude 代寫靠的是內建的 plugin-authoring skill。官方描述它會告訴 Claude 三件事：Mod 該寫在哪裡、你這個版本有哪些事件與方法、以及 Mod 怎麼被載入。你可以直接描述需求，Claude 在需要時自己載入這個 skill；也可以自己在提示符輸入 /plugin-authoring 讓它載入。上一章的內建 Mod 表提到，這個 skill 是由 cc-plugin-plugin-authoring 帶進來的，它只有 skill、沒有 Mod 程式碼，可以在 /plugin 停用。

怎麼下需求：描述你要看到什麼，不要描述 API

一篇整理官方文件的指南建議：用白話描述你想看見的結果，而不是你以為需要的 API。它舉的例子是：

需求範例
show the current git branch above the prompt

同一篇也指出，claude.dev 的教學範例只描述顯示的內容，狀態如何保存、該掛哪些事件、怎麼驗證，是 skill 負責的事。另一支影片（VID-322）的示範也是同樣的風格：在 Desktop 的 Code 分頁建一個空資料夾、信任它，然後直接講需求，例如「在側欄做一個焦點卡，中間一個數字，點一下會累加，要能清除與關閉」。同一支影片另一個示範是一句「我剪稿時右側用彩色長條顯示每段時間……可即時更新」，就做出配音時間軸工具。

💬

描述你想看見的結果，不要描述你以為需要的 API：事件怎麼掛、狀態怎麼存，是 skill 的工作。

我自己的 obs-log-timer 是用比較完整的提示做出來的。它的需求本身有明確的邊界條件（時間、什麼情況不送、要不要測試），所以我把這些全寫進去：

我給 Claude 的需求
/plugin-authoring 做一個 mod：每天 12:00 和 17:00（台北時間），在執行中的 Claude Code session 閒置時，自動執行 /write-obs-log，把這段對話整理寫入 Obsidian 工作日誌。非互動 session 不送，同一時段只送一次，並寫測試。

好的需求有三個元素：Mod 要出現在哪裡或做什麼、什麼情況下不該動作、要不要測試。後兩項在第 10 章討論測試時你會發現特別重要。

核准流程：兩次點頭與一次確認

Claude 寫 Mod 的過程不是無聲完成的，依官方文件與整理指南，有兩次需要你點頭、一次事後確認的步驟：

  1. 逐檔核准。Claude 把 Mod 寫進這個 session 專屬的資料夾，一篇指南寫它是 ~/.claude/dev-mods/ 加上 session ID。因為 ~/.claude 是受保護路徑，在 default 與 acceptEdits 權限模式下，每建立一個檔案 Claude Code 都會先問你。
  2. 啟用熱重載。Claude 存第一個檔案時，Claude Code 會問「Enable hot reloading for this session?」，選 Enable for this session 之後，那個資料夾裡的 Mod 在回合結束時載入，之後每個修改過它的回合結束再重載。
  3. 確認載入。執行 /plugin，在 Installed 分頁看得到這個 Mod，也能在那裡關掉它。

VID-322 特別提醒：熱重載的提示必須你自己在畫面上點「Allow」，權限規則不會替你自動授權。這個設計是對的：Mod 沒有沙箱，Claude 剛寫出來的程式碼更該由你親手放行。

⚠️
這些 session 不會載入 Claude 寫的 Mod

依官方 Create a mod 頁面，以下情況 Claude 寫的 Mod 不會載入：沒有人能核准（claude -p 或 dontAsk 模式）、工作區尚未信任、Mod 被停用（--safe-mode、--bare、disableAllHooks，或組織的 managed settings 阻擋）。如果組織設了上一章的 allowManagedModsOnly，連 Claude 在 session 裡代寫的 Mod 也不會跑。

保存：Claude 寫的 Mod 只活在那個 session

官方文件講得很清楚：Claude 寫的 Mod 只在寫它的那個 session 載入，而且 session 的 mods 資料夾超過 cleanupPeriodDays 就會被刪掉。要留下來，就得把整個目錄複製到你自己的位置（文件舉的例子是 ~/mods/git-branch），再選擇載入方式：自己啟動的 session 用 --plugin-dir，要給別人用就放進 marketplace。

bash
# 把 session 的 mods 資料夾裡的 Mod 複製到自己的位置
# （session id 與資料夾結構依你的實際情況調整）
cp -r ~/.claude/dev-mods/<session-id>/git-branch ~/mods/git-branch

# 之後在你自己啟動的 session 載入
claude --plugin-dir ~/mods/git-branch

第一行的 cp 是我依文件說明寫出的做法，文件本身只說「複製目錄」。另一篇教學還說，Qiita 與 Zenn 的作者回報 dev-mods 資料夾大約 30 天後隨舊 session 一起被清掉；這是社群回報，官方的依據是 cleanupPeriodDays，以後者為準。StationX 的指南另外提到，把做好的 Mod 手動丟進那個資料夾並不是文件記載的做法，它試過，一開始「沒反應」（Unknown command）；已有的 Mod 就用 --plugin-dir。

💬

Claude 寫的 Mod 只活在寫它的那個 session：不把目錄複製出來，等 cleanupPeriodDays 一到就一起被清掉。

Desktop 沒有旗標：用環境變數

Desktop app 不能帶 --plugin-dir。社群教學的做法是在 ~/.claude/settings.json 的 env 區塊設 CLAUDE_CODE_PLUGIN_DIRS，且專案層級的設定會被忽略。我自己的 Windows 設定長這樣，路徑用正斜線、多個 Mod 以分號分隔：

~/.claude/settings.json
"env": {
  "CLAUDE_CODE_PLUGIN_DIRS": "C:/Users/porte/.claude/mods/obs-log-timer;C:/Users/porte/.claude/mods/herdr-watch"
}

請 Claude 改它寫過的 Mod

要修改已經存在的 Mod，官方的做法是啟動 session 時用 --plugin-dir 指向 Mod 目錄（claude --plugin-dir ./first-mod），這樣 Claude 寫的改動會在同一個 session 載入。Claude 會編輯 hooks module、跑 claude plugin validate、並修正它回報的問題；Claude 在回合內存的檔案，回合結束就重載，所以它做完你就能試。由於用 --plugin-dir 載入的目錄是受保護路徑，default 與 acceptEdits 模式下，Claude 的每次編輯仍要你核准。

我維護 obs-log-timer 時，用的是同一個格式：指名資料夾、說清楚要改什麼、要求測試同步更新並跑測試。

修改需求
/plugin-authoring 修改 C:\Users\porte\.claude\mods\obs-log-timer：把觸發時間改成 HH:00 和 HH:00，測試一起更新，跑 claude plugin test 確認通過。

拿到程式碼後：先驗收，再相信

整理指南的一句話值得抄下來：即使你打算以後都手寫 Mod，也先從 Claude 代寫開始，讀它產生的程式碼，再跑驗證指令。代寫的 Mod 在你放行之前，你只信得過它「看起來對」，所以我的驗收清單是三步：

bash
claude plugin validate ~/mods/git-branch
claude plugin test ~/mods/git-branch
  • 看 hooks: 與 calls: 兩行。它掛了哪些事件、呼叫了哪些 $ 方法，要和你的需求對得上。想做一個狀態列卻出現 $.http.fetch，就要問為什麼。
  • 跑 claude plugin test。它不需要 session、登入或網路。有測試，才有東西能確認你之後的修改沒有弄壞它。
  • 讀程式碼本身。第 6 章的審查原則同樣適用於 Claude 寫的 Mod：它的權限和你一樣。
ℹ️
Claude 也會踩 API 的坑

我在開發 obs-log-timer 時記下三個坑：要執行 slash 指令得用 $.command.run，因為 $.prompt.submit 不能送以 / 開頭的文字；測試的 tier() 只接受 prepend、user、append、builtin；測試裡的 ui.toast hook 要回傳 { value: undefined }，不能回 {}。這些是我的實測紀錄，不是官方列表，所以先跑 validate 與 test 比憑印象判斷可靠。

小結

  • 代寫流程：描述結果 → 逐檔核准 → Enable hot reloading → /plugin 確認。
  • 成品只活在那個 session，要保存就複製目錄，再用 --plugin-dir、CLAUDE_CODE_PLUGIN_DIRS 或 marketplace 載入。
  • 代寫不等於免審：validate、test 和讀程式碼，一個都不能省。

下一章我們不再依賴 Claude：從 plugin.json、hooks.json 到 register，親手把一個 Mod 寫出來，你會發現剛剛 Claude 寫的東西，結構其實就這麼簡單。
