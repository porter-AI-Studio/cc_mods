第 3 章 · Part 1：認識 Mods

Mods 怎麼運作：事件、三種處理方式與執行環境

Mod 的運作模型：事件、處理方式與執行環境

一個 Mod 是常駐的函式模組

第一章看過最小的 Mod：一個匯出 register(on, options) 的 hooks module。Claude Code 載入 plugin 時呼叫 register 一次，你在裡面呼叫 on 註冊 hook。之後這個模組一直留在 session 裡，頂層的變數也就一直活著，這就是第一章 calls 計數器能跨事件累加的原因。register 的第二個參數 options 放的是 manifest 裡 userConfig 欄位的值，已補上預設值。

檔案副檔名可以是 .js、.mjs、.cjs、.jsx、.ts、.mts、.cts 或 .tsx，內容必須是 ES module。官方文件說明你不需要 Node.js、打包工具或建置步驟，Claude Code 直接載入 .js 與 .ts 檔。

事件、hook 與三個參數

Claude Code 在每個關鍵時刻發出一個事件，例如 Claude 要用工具、使用者送出 prompt、一個回合開始、介面某一塊要畫。Mod 的 hook 就掛在事件上，每個 hook 收到三個參數：

💬

e 是凍結的事件輸入，next 會把事件交給下一個處理者：要改寫就送一份副本，要截斷就別呼叫 next。

  • $：mods API。hook 要做事，只能透過它，包括畫介面、讀寫檔案、啟動程序、發網路請求、呼叫模型。
  • e：事件的輸入，是深度凍結的純資料，直接指派欄位會丟出錯誤；要修改就傳一份副本給 next。
  • next：下一個處理者。同一個事件上所有 hook 串成一條 middleware 鏈，next(e) 會呼叫鏈上的下一個 hook，鏈的末端才是 Claude Code 自己的行為，回傳值就是事件的結果。

事件的種類很多，下表只挑各組有代表性的幾個，完整清單以 Mods reference（以 v2.1.290 為準）為準：

分組代表事件什麼時候觸發
工具tool.call、tool.check、tool.describe工具即將執行；Claude Code 決定是否放行；工具說明第一次送給 Claude
Promptprompt.submit、prompt.section、prompt.contextprompt 送出；系統提示的每個區段；每段對話第一則訊息附帶的 context
指令與設定command.run、config.set指令即將執行；/config 的一列即將改變
回合turn.start、turn.step、turn.complete回合開始；每一次要送給模型的請求；回合結束
Sessionsession.start、session.end、session.compact每個 Mod 載入時一次；session 結束或 /clear、/resume、/branch；對話即將壓縮
子代理agent.offer、agent.spawn子代理類型被提供給 Claude；子代理或 agent team 隊友即將啟動
介面ui.render、ui.press、ui.input某個 render site 即將繪製；使用者操作了 Mod 畫出的按鈕或輸入框
其他 Modplugin.register、engine.create某個 hooks module 即將載入；mods API 正在為這個 Mod 建立
settings hookclassic.Stop、classic.PostToolUse每個 settings hook 事件都有一個 classic. 開頭的對應事件，e 是 stdin 的 JSON

另外，mods API 的每個方法本身也是事件，名稱就是命名空間加方法，例如 fs.read、model.complete、ui.open。掛在這些事件上的 hook，能攔截排在它後面的 Mod 發出的呼叫，後面談多個 Mod 組合與安全審查時會用到這個機制。

三種處理方式：觀察、改寫、接管

hook 如何使用 next，決定它在做哪一種處理。Claude Code 在行動之前先執行 hook，所以是 hook 決定接下來發生什麼事。

觀察（observe）

做完自己的事，回傳 next(e)，事件原樣繼續。下面這個 hook 在每個工具執行前，於對話記錄裡留下一行暗色的訊息：

觀察：工具執行前記錄
on('tool.call', async ($, e, next) => {
  // Runs before the tool does
  $.ui.log('Claude is about to use ' + e.tool)
  // Pass the event on unchanged
  return next(e)
})

想在事件之後做事，就 await next(e)，等結果回來再處理，最後把結果原封不動回傳。因為回傳的是 next(e) 解析出的值，Claude 讀到的內容不變。

改寫（rewrite）

把修改過的副本傳給 next。後面的 hook 與 Claude Code 只看得到改過的版本，永遠看不到原本的事件：

改寫：送出前去掉 prompt 前後空白
on('prompt.submit', async ($, e, next) => {
  // Pass on a copy of the event with its text changed
  return next({ ...e, text: e.text.trim() })
})

接管（answer）

不呼叫 next，直接回傳結果。鏈被截斷，後面的 Mod 與 Claude Code 自己的行為都不會執行：

接管：拒絕所有 Bash 指令
on('tool.call', { tool: 'Bash' }, async () => {
  // No call to next, so the command never runs
  return { deny: 'Bash is turned off in this project. Use the file tools.' }
})

Claude 嘗試 Bash 指令時，指令不會執行，Claude 讀到的是 deny 的文字，把它當成工具的結果。每個事件可回傳的結構不同，例如 tool.call 可回 { deny: reason } 或 { result }，prompt.submit 則是 { drop: reason }。不能把一個事件的拒絕格式搬去另一個事件，要查 reference 的「A hook can return」欄。

用 matcher 縮小範圍

on 的第二個參數是 matcher，它是一個物件，欄位會與事件的欄位比對，全部符合時 hook 才執行。欄位值可以是字串、陣列或正規表示式：

matcher 的三種寫法
// A string matches one value: Bash calls only
on('tool.call', { tool: 'Bash' }, hook)
// An array matches any value in it: Edit calls and Write calls
on('tool.call', { tool: ['Edit', 'Write'] }, hook)
// A regular expression matches by pattern: every tool of one MCP server
on('tool.call', { tool: /^mcp__github__/ }, hook)

事件名稱也可以用萬用字元：'classic.*' 比對所有 settings hook 事件，'*' 比對所有事件（telemetry 事件除外）。同一個事件、沒有 matcher 的情況下不能註冊兩次，否則模組載入失敗，所以 session.start 要做的事都放進同一個 hook。

多個 Mod 的順序與失敗處理

同一事件上的 hook 組成一條鏈，第一個 Mod 在最外層：它先看到事件、最後看到結果，並決定後面的 Mod 要不要執行；後面的 Mod 無法阻止前面的 Mod 看到事件。Claude Code 依來源決定順序：

  1. 內建的守衛 sec-default@builtin、組織以 prependPlugins 列出的 Mod，以及其他算作組織的 Mod。
  2. 你安裝的 Mod。
  3. 組織以 appendPlugins 列出的 Mod。
  4. 其他內建的 Mod。
💬

鏈上第一個 Mod 最先看到事件、最後看到結果；後面的 Mod 再怎麼努力，也擋不住前面那一個的眼睛。

在你安裝的 Mod 之間，一個 Mod 會排在它於 manifest 的 dependencies 裡列出的 Mod 之前；同一個模組裡，則依 register 呼叫 on 的順序。

hook 失敗（丟出錯誤、逾時、或回傳錯誤的結構）時，不會弄壞整個 session，但後果取決於它有沒有呼叫過 next：在呼叫 next 之前失敗，Claude Code 略過它，換下一個處理者；在 next 完成之後失敗，結果維持，不會重跑。也就是說，守門型的 hook 在尚未呼叫 next 就失敗時，預設會被略過、不再阻擋（等於放行）。要改成「失敗時拒絕」，就用 .catch 掛一個錯誤處理函式：

失敗時拒絕的 .catch
// on returns a registration, and .catch attaches a handler to that one hook
on('tool.call', { tool: 'Bash' }, guard).catch(async ($, e, next) => {
  // guard had already called next, so return what came back
  if (next.called) return next(e)
  // next.error.kind says why the handler was asked, such as 'throw' or 'timeout'
  return { deny: 'The command guard failed, so this command was not run: ' + next.error.kind }
})

next.called 讓處理函式分辨失敗前有沒有呼叫過 next，next.error.kind 說明原因，例如 throw 或 timeout。.catch 函式本身也有 1 秒的時間限制。

💬

Saltzer 與 Schroeder 的 fail-safe defaults 主張存取決策應以許可為依據，預設無權存取；本書據此檢視 Mod：守門 hook 在呼叫 next 之前失敗卻預設放行，若要失敗時拒絕，就得自己用 .catch 補上。

出處：J. H. Saltzer、M. D. Schroeder，〈The Protection of Information in Computer Systems〉，《Proceedings of the IEEE》63(9)，1278–1308，1975，I.A.3「Fail-safe defaults」；套用到 Mod 守門 hook 是本書改編。

執行環境與限制

hooks module 本身沒有 Node.js API、沒有 setTimeout 之類的計時器全域函式，也沒有自己的網路與檔案存取。可用的是標準 JavaScript 與 Web API，如 URL、TextEncoder、AbortController、crypto.subtle。要碰外部，一律走 $：檔案用 $.fs、程序用 $.process、網路用 $.http、計時用 $.clock、跨 session 的儲存用 $.store。

⚠️
這不是權限隔離

「沒有 Node、沒有 DOM」限制的是 API 的取得方式，不是權限。官方文件寫得很清楚：Mod 透過 mods API 讀寫檔案、啟動程序與網路請求時，權限與執行 Claude Code 的你完全相同，而且 Mod 沒有沙箱。正因為所有對外接觸都經過 $，claude plugin validate 才能靜態列出 Mod 會用到哪些呼叫，第四章會用它做安裝前審查。

hook 與 API 呼叫也受時間與大小限制，超過時間限制的 hook 會被略過。常用的幾項如下（數值取自 Mods reference）：

項目限制
一個 hook 處理一個事件的執行時間（不含 next 與 mods API 呼叫的等待）10 秒；prompt.edit 的 hook 為 50 毫秒
$.process.run 逾時預設 30 秒，最長 10 分鐘
$.fs.read／$.fs.write單一檔案 4 MiB
$.http.fetch請求與回應本文各 4 MiB，一次呼叫（含重新導向）30 秒，最多跟隨 5 次重新導向
$.store全部合計 4 MiB 的 JSON

Mod 會在哪裡跑、畫在哪裡

Mod 的 hook 在每一種載入該 plugin 的 session 裡都會執行，但畫出來的東西只在終端機與 Desktop app 看得到：

執行位置hook 是否執行Mod 畫的東西是否出現
終端機的 claude（含編輯器內建終端機、JetBrains plugin）是是
Desktop app 的 Code 分頁（WSL session 除外）是是，但 elements 表標記為「僅終端機」的元素除外
Desktop app 的 WSL session否，WSL session 沒有 plugin否
VS Code 擴充套件的聊天面板是否
claude -p 與 Agent SDK是否
Remote Control（claude.ai 或手機 app）是，在你機器上的 session 裡在你機器上的終端機
雲端 session是，但 plugin 必須能傳到雲端 session否

需要畫介面的 Mod，應該檢查自己跑在哪個 app，在不能畫的地方改成對話記錄裡的一行文字或指令的文字回覆。Mod 畫介面時，是對 Claude Code 定義好的 render site 做事，像 Pane（對話記錄旁）、AbovePrompt（輸入框上方）與 Spinner、ToolUse 等，由 ui.render hook 回傳元素樹；細節留到第九章。

ℹ️
事件名稱要照官方拼法

預覽期的文章與部分影片逐字稿用過大寫的事件名稱（如 Tool.Call）或其他的稱呼。實際在程式碼裡，事件名稱是小寫點分格式的字串，像 tool.call、ui.render。名稱拼錯時，claude plugin validate 會回報 "tool.calls" is not an event 這類錯誤，Claude Code 也不會呼叫那個 hook。

小結

一個 Mod 是常駐於 session 的函式模組：在事件上掛 hook，每個 hook 靠 $ 對外做事、靠 e 看事件、靠 next 決定觀察、改寫或接管。多個 Mod 串成一條鏈，順序由來源決定，失敗時預設略過。這個執行環境沒有 Node 與 DOM，但沒有降低權限，所以安全責任仍在安裝者身上。
