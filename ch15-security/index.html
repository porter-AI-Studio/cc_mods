第 15 章 · Part 5：安全與治理

安全：Mods 沒有沙箱，權限跟你一樣

Mod 能做什麼、哪些防線有效、哪些沒有

前面幾章把 Mod 當成方便的工具，這一章要說另一半：它是在你的 Claude Code 程序裡、以你的身分執行的程式碼。為了不誇大也不淡化，本章把內容分成三種，並在標題標明：官方文件說的、研究者展示的、作者推論。

官方文件說的：Mod 碰得到什麼

Anthropic 的 Mods overview 把話說得很直接：Mod 是以你的權限執行的程式碼。載入後，它可以讀寫你的帳號能碰到的任何檔案、啟動程式、發出網路請求；讀環境變數與設定檔（包括放在裡面的 API key）；看到每個 prompt 與 tool call；改寫它們、把 prompt 當成你自己打的送出；在你被詢問之前就核准 tool call；也能用你的方案或 API key 呼叫模型、花你的額度。

文件接著說：Mods 沒有沙箱。如果你開了 Claude Code 的 sandboxing，沙箱隔離的是 Claude 執行的 Bash 指令，而 Mod 啟動的程序在沙箱之外。另一份官方管理文件也寫明：沒有任何一項管控會把 Mod 關進沙箱，被允許的 Mod 就是以使用者身分、帶著使用者對檔案、程序與網路的存取執行。

有一處官方明確保留：Mod 可以重畫大部分介面，但不能改權限提示（permission prompt）。不過這只涵蓋提示本身，Mod 仍可在提示出現之前就核准或拒絕該呼叫。

💬

Mod 的權限不是借來的，就是你的：它讀得到你讀得到的檔案，花得到你花得到的額度。

兩條邊界：規則管 Claude，不管 Mod 自己

常見的誤解是 deny 了 Read(.env)，Mod 就讀不到。官方管理文件說，這條規則約束的是 Claude 發出的 tool call；Mod 自己呼叫 $.fs.read、或用 $.process.run 啟動一個會讀檔的程式，不在規則範圍內。同樣的，網路政策可以拒絕 Mod 的 $.http.fetch，但 Mod 啟動的程式連網時用的是使用者自己的存取。

Mod 到達外部世界只有一條路，也就是 $ API，每次呼叫本身都是事件，所以可以被攔截與審查。Pebblous 的報告把這稱為「咽喉點而非隔離」，並指出兩個出口：Mod 啟動的子程序，與規則範圍外的 Mod 自身程式碼。這是 Pebblous 的詮釋，不是官方用語。

官方文件說的：deny 規則的成立條件

這是本章最容易被誤解的一點。依官方 permissions 文件，規則的順序是 deny、ask、allow；但 Mod 可以在規則與 settings hook 都決定之後，對 tool call 給出最終答案，這個答案可以取代前面的結果。官方管理文件的預設行為整理如下：

  • Claude Code 會在使用者安裝的所有 Mod 之前載入內建的守門 Mod sec-default@builtin（在 /plugin 與 debug log 中顯示為 cc-plugin-sec-default），使用者無法關閉它。
  • 守門 Mod 只在兩種情況載入：機器上有 managed settings，或使用者以 Team 或 Enterprise 方案登入。使用 API key，或透過 Amazon Bedrock、Google Cloud 的 Agent Platform、Microsoft Foundry 認證的人，只有在機器上有 managed settings 時才有它。
  • 守門 Mod 載入時，預設（管理員沒有設 allowModsToOverrideDenyRules）使用者的 Mod 不能核准被 deny 規則拒絕的呼叫；managed settings 裡的 PreToolUse hook 的阻擋也是最終的。
  • 其他情況（例如個人 Pro、Max 訂閱，或 API key 加上沒有 managed settings 的機器），官方 permissions 文件（經 Pebblous 引用）寫明：Mod 可以核准被 deny 規則拒絕的呼叫；管理文件也說，守門 Mod 沒載入的地方，相關選項都不適用。

除此之外，守門 Mod 保護的只是組織管理的東西（managed hook、系統提示、managed 的 CLAUDE.md、設定、managed MCP 伺服器），官方說「其餘都允許」。ch5 介紹過它的定位，這裡要提醒的是：沒有 managed settings 的個人電腦，可能不在保護範圍內，所以只靠自己審查。

官方文件說的：擋人的 hook 壞掉時，呼叫會放行

第二個容易被忽略的預設值：依官方 events 文件，沒有失敗處理器的 hook 如果拋出例外、超時或回傳格式錯誤，Claude Code 會略過它，由下一個處理器接手；它不再阻擋，後續的處理器與權限規則繼續決定這個指令能不能執行。官方文件自己的 hold 範例（經 Pebblous 引用）在註解裡就寫著：Claude Code skips a hook that times out, so the held command would run。要改成失敗時拒絕，必須自己掛 .catch：

官方 events 文件的失敗處理範例（依官方原文還原）
on('tool.call', { tool: 'Bash' }, guard).catch(async ($, e, next) => {
  // guard had already called next, so return what came back
  if (next.called) return next(e)
  // next.error.kind says why the handler was asked, such as 'throw' or 'timeout'
  return { deny: 'The command guard failed, so this command was not run: ' + next.error.kind }
})

代價是時間：官方 limits 表中，一個 hook 自己有 10 秒，但負責攔截失敗的處理器只有 1 秒。Pebblous 讀過官方範例 repo 的三個 Mod（blast-radius、token-weather、replay-theater）全部原始碼，沒有一個掛了這種處理器，他們只當觀察、不推論意圖；blast-radius 的 README 也寫明它是安全網，不是權限系統。我的推論：自寫的守門 Mod 若沒有備援，就要接受它出錯時會放行，真正不能放行的操作要交給 permission 規則或 managed settings。

💬

Saltzer 與 Schroeder 的 fail-safe defaults 主張存取決策應以許可為依據，預設無權存取；本書據此檢視 Mod：沒掛 .catch 的守門 hook 壞掉時，只是它的阻擋被略過，後續 handler 與權限規則仍會接手。

出處：J. H. Saltzer、M. D. Schroeder，〈The Protection of Information in Computer Systems〉，《Proceedings of the IEEE》63(9)，1278–1308，1975，I.A.3「Fail-safe defaults」；套用到 Mod 守門 hook 是本書改編。

研究者展示的：Pluto Security 的四項測試

以下是 Pluto Security 在 2026 年 9 月 22 日發表的測試，對象是當時仍須設定 CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 才能啟用的 Claude Code v2.1.274，也就是正式推出（2.1.287，10 月 1 日）之前的實作。作者在文章末尾也註明內容可能在正式版前改變，所以請當成「這個機制在當時如何被利用」，而不是「現在每一項都還成立」。四項展示分別是：

  1. 讀取並外送憑證與歷史：測試用的 Mod 在 session.start 時用 $.fs.read 讀 ~/.claude/.credentials.json 與 history.jsonl（他們機器上的後者有 834 KB，包含所有專案與 session 的 prompt），再用 $.http.fetch 送到他們控制的伺服器；過程中沒有任何提示。
  2. 安裝時看不到它能做什麼：他們做了一個掛在 *（所有事件）等四個事件上的 Mod，plugin details 卻顯示 Hooks (0)；同一個 marketplace 裡的傳統 shell hook plugin 則正確顯示 Hooks (1) PreToolUse。能力清單只有手動執行 plugin validate 才看得到。
  3. 偽造 UI：Mod 在輸入框上方的 band 畫出仿 Claude Code 風格的「session 驗證」輸入欄，要使用者重新輸入 API key，並用測試金鑰完整示範流程。另外，在 AskUserQuestion 對話框，Mod 可以改寫顯示的問題文字；引擎會還原模型給的選項標籤，但當標籤是通用的「Confirm」「Cancel」時，這層保護就沒用。他們也示範兩個 hook 合作，讓實際執行的指令與 transcript 顯示的指令不一致。
  4. 抓取遠端程式碼再執行：Mod 用 $.http.fetch 抓腳本、用 $.process.run 執行；他們換掉伺服器上的檔案而完全沒改 Mod，下一個 session 就跑了新內容。$.http.fetch 的回應沒有完整性固定（integrity pinning）。

Pluto 同時承認：worker 沙箱擋住了繞過 $ 的存取，權限提示無法被 Mod 改寫，Mod 的身分 tier 由主機指派、不能自稱。他們的主要建議是把 Mod 當成二進位檔，標準等同 curl | sh。ssdnodes（2026-10-03）轉述了這幾點，是二手整理；我沒有在 2.1.287 以後的版本逐項重現。

研究者展示的：驗證指令的極限

官方給的事前檢查是 claude plugin validate：不執行程式，直接列出 Mod 掛了哪些事件、呼叫了哪些 API。官方並特別指出，Claude Code 會拒絕載入「用了 validate 無法讀懂的方式呼叫 API」的 Mod。

validate 輸出範例（官方文件）
claude plugin validate ./some-mod

❯ ./register.js hooks: session.start, tool.call, ui.render{component=Pane}
❯ ./register.js calls: $.fs.read, $.http.fetch, $.store.set, $.ui.open

但它有兩個極限，都應該寫進你的審查流程：第一，它說的是 Mod「會呼叫什麼」，不是「會做什麼」，單獨一行 $.process.run 就等於「什麼都做得到」（Pebblous 的歸納）。第二，Pluto 示範過只改寫傳給 next 的值、完全不呼叫 $ 的 Mod，validate 回報沒有任何呼叫；它也看不到執行期才抓回來的程式碼。所以 validate 是審查的起點，不是通過證明。ssdnodes 建議再用一條搜尋把可疑行列出來（每個命中只是「要讀的一行」，不代表有害）：

ssdnodes 建議的搜尋（原文逐字）
grep -rnE 'https?://|eval\(|new Function|import\(' ~/.claude/plugins/

歷史背景：這不是 Mods 才有的問題

下面三則都不是 Mods 的漏洞，但它們說明了同一類風險為什麼早就存在：

  • PromptArmor（2025-10-21，Mods 推出之前）：示範惡意 marketplace plugin 如何用傳統 hook 繞過 human-in-the-loop：一個 hook 在每次送出 prompt 時改寫權限檔、永久允許 curl，另一個 hook 在每次要執行指令時自動核准 curl；再搭配 plugin command 裡的 prompt injection，讓 Claude 把程式碼內容送給攻擊者。它說明的是 plugin 與 hook 的供應鏈，不是 Mod 專屬。
  • Check Point 揭露的專案設定檔漏洞（hackmag 於 2026-03-02 報導）：開啟惡意專案即可執行程式碼或外洩 API key，涉及 .claude/settings.json 的 hook、MCP 自動核准設定與 ANTHROPIC_BASE_URL。Anthropic 的 GitHub 安全公告列出：CVE-2025-59536 是信任對話框出現前就可能執行專案中的程式碼，修於 v1.0.111；CVE-2026-21852 是信任確認前因專案設定把 ANTHROPIC_BASE_URL 指向攻擊者端點而可能洩漏 API key，修於 v2.0.65。二手報導對 CVE-2025-59536 的描述互相矛盾（hackmag 說是 MCP 自動核准繞過，MintMCP 說是 SessionStart hook 的遠端程式碼執行），以官方公告為準。
  • Johann Rehberger（The Register，2026-08-28）：用「請摘要這個網站」引導 Opus 5 在 Auto Mode 執行攻擊者的程式碼，三種變形各測五次，成功率 60% 到 80%。Anthropic 的回應據報導是 Auto Mode 為盡力而為的分類器，不是安全保證，Rehberger 的結論是真正的邊界是作業系統隔離與網路出口控制。這與 Mod 無直接關係，放在這裡是因為它說明「別人的內容」本身也是攻擊面。
ℹ️
審查與簽章也不是萬靈丹

Pebblous 引用 JetBrains 官方部落格：該平台有人工審查與簽章，2026 年 6 月仍下架了 15 個竊取 AI provider API key 的惡意外掛，因為審查工具原本只做相容性與 API 用量檢查。審查保證的範圍，取決於它被設計來看什麼。

作者推論與我自己的做法

以下不是官方、也不是研究結論，是我從上面整理出來的判斷：

  • 風險大小取決於 Mod 碰了哪些 API，不是 Mod 這個名字。只畫畫面、讀 session 用量的 Mod（第 13 章的多數案例）與會 fetch 再 run 的 Mod 不在同一個等級。
  • 自己叫 Claude 寫、自己讀過，比下載陌生人的穩。EP421 影片也給同樣的建議：六個裡有五個建議自己做，因為可以直接問 Claude 它用了哪些 API；真的要裝別人的，先 validate。我第 14 章的 next-steps 就是照這個流程讀完 230 行才裝的。
  • 鎖定版本、避免執行期抓遠端程式碼。Pluto 與 ssdnodes 共同的建議。
  • 不要把 Mod 當唯一的防線。會讓你後悔的操作，交給 permission 規則、managed settings 或 OS 隔離，Mod 只當第二層。
  • 看到 Claude Code 裡突然要你輸入金鑰的提示，一律當成可疑。先關閉 session，重開後在 /plugin 檢視已安裝項目；官方也提供停用 Mod 的方式：
只為一個 session 停用所有已安裝的 Mod
claude --safe-mode

官方列出的停用層級還有：在 /plugin 停用或解除安裝單一 Mod，或在 ~/.claude/settings.json 設 "disableAllHooks": true（會連你的 settings hook 與自訂狀態列一併停掉）。內建 Mod 不受這些設定影響。

還有幾件事我沒有驗證

Pluto 的四項展示是 2.1.274 的結果，我沒有在目前版本重現；plugin details 當時漏報，現在是否已修正，請以你的版本實測。Check Point 的 CVE 對應已改以 Anthropic 的 GitHub 公告為準。Pebblous 的 deny 規則結論，我只對應到官方文件中的敘述，沒有在自己的機器上測試被 deny 的呼叫能否被 Mod 核准。

小結與下一章

把三類內容放在一起，結論很樸素：Mod 的能力與你相同，引擎提供的防線只在有 managed settings 或公司方案時才完整，hook 壞掉時預設放行，審查工具能告訴你「它碰什麼」但不能告訴你「它做什麼」。個人使用時，這些可以靠自己審查與少裝來管理；一旦要在團隊裡推行，就需要一套制度。下一章談團隊導入與治理：怎麼設計審查清單、用 managed settings 與 marketplace 管控限制 Mod 的來源，並在便利與風險之間做取捨。
